# M21 Phase 2 Strategy — Deploy and Cutover

Status: Draft for review — execution not started.
Drafted: 2026-09-05.
Parent milestone: [`21_OB_DEPLOYMENT.md`](../milestones/21_OB_DEPLOYMENT.md)
Prerequisite: [`21.1_PRE_DEPLOY_VERIFICATION.md`](21.1_PRE_DEPLOY_VERIFICATION.md) complete.
Next phase: [`21.3_ROLLOUT_VERIFICATION_SIGNOFF.md`](21.3_ROLLOUT_VERIFICATION_SIGNOFF.md)

Goal: serve the open beta from `https://cryptozing.app` with the approved legal layer, correct mail/public-link configuration, and the existing content URLs intact.

The Agent owns the serial cutover and shared production configuration. `Guided User` handles account-console actions when needed; `User` accepts the cutover window and release readiness. A subagent may check public URL responses after each completed change; it must not edit DNS, integrations, or the VPS concurrently.

Use the VPS invocation and two-Compose-file rules in [M21.1](21.1_PRE_DEPLOY_VERIFICATION.md#execution-and-ownership). Keep the running app, queue, and scheduler on the same app tag and environment. The production watcher is scheduled inside the scheduler.

2. [ ] [Agent] Record the current target's `WALLET_NETWORK`, `APP_PUBLIC_URL`, and `MAIL_ALIAS_ENABLED`; identify the box before any destructive operation.

4. [ ] [Agent] Confirm the prior hostname remains available for existing links and delayed mail callbacks under the Phase 1 plan.
5. [ ] [User] Accept the cutover window and the prepared go/no-go result.

## 2. [ ] Finalize legal publication and release artifacts

1. [ ] [Agent] Read the system date for the actual publication and replace the remaining effective-date placeholders in the reviewed ToS and Privacy Policy copies.
2. [ ] [Agent] Resolve cross-policy links and synchronize the tracked drafts, app Markdown, and any content-repo copies with the approved wording and actual analytics setup.
3. [ ] [Agent] Verify `/terms` and `/privacy` are readable without login and the signup, wallet, invoice, and footer placements match M19.5.
4. [ ] [Agent] Commit/push the synchronized release edits according to each repo's rules; complete required PR/tests for changes beyond the doc/copy carve-out.
5. [ ] [Agent] Pin the resulting app/site artifacts and verify them before they serve public traffic. Apply the repository's Sunday commit/push restriction when selecting the cutover window.

## 3. [ ] Prepare apex serving and TLS

Normal apex traffic stays on Pages until §5. Phase 1's challenge plan must support certificate issuance before that traffic moves.

1. [ ] [Agent] Obtain and verify the required apex/redirect-host certificate using the prepared challenge path.
2. [ ] [Agent] Set `CZ_SERVER_NAME=cryptozing.app` and activate the reviewed apex/retained-alpha nginx configuration with the separate site container and approved content artifact; preserve the current app/worker release until §4's migration step.
3. [ ] [Agent] Verify HTTPS and the intended HTTP/`www` redirects directly against the VPS using the intended hostnames and SNI.
4. [ ] [Agent] Check `/learn/*` and required assets through that host-aware route against the Phase 1 baseline.
5. [ ] [Agent] Configure renewal for the running nginx, switching standalone renewal to webroot where required. Public renewal proof follows the DNS switch in §5.

## 4. [ ] Activate the application configuration with processing held

Keep the alpha gate enabled until the public-host smoke passes. Hold outbound mail and queue/scheduler processing through §5's DNS/callback checks.

1. [ ] [Agent] Quiesce queue/scheduler work and account for in-flight work before proceeding.
2. [ ] [Agent] Disable outbound mail in the running app for the configuration change.
3. [ ] [Agent] Set `APP_URL=https://cryptozing.app` and confirm `APP_PUBLIC_URL` resolves to the same value.
4. [ ] [Agent] Verify `WALLET_NETWORK=mainnet`, production aliasing off, `MAIL_ALIAS_DOMAIN` cleared, and the verified donation configuration retained.
5. [ ] [Agent] Run pending migrations once, before bringing services up on the new app image; preserve the existing mainnet database.
6. [ ] [Agent] Recreate the app and serving services with the pinned release and updated environment. Recreate queue/scheduler containers without starting their processing, and verify both remain stopped; an unrestricted `up -d` would resume them.
7. [ ] [Agent] Run `wallet:check-config` and verify the source-wallet comparison remains applicable to the deployed keys.
8. [ ] [Agent] Verify the final app release, legal pages, and public/content routes directly against the VPS using the apex hostname before directing public traffic to it.

2. [ ] [Agent] Check authoritative and independent recursive responses for the intended targets, including any published AAAA record.

4. [ ] [Agent] Prove certificate renewal and its nginx reload hook against the public challenge route.
5. [ ] [Agent] Retarget Mailgun's `delivered`, `temporary_fail`, and `permanent_fail` registrations to `https://cryptozing.app/webhooks/mailgun`.

   2. [ ] Start queue/scheduler processing and confirm the running services report those values.
7. [ ] [Agent] Send an operator-addressed invoice and reviewed paid receipt; verify apex links, received mail, and truthful callback-driven delivery state.

## 6. [ ] Open access and complete the cutover smoke

1. [ ] [Agent] Verify the app landing page, policy URLs, content routes, and indexing split on the apex while the alpha gate still protects app access.
2. [ ] [Agent] Set `ALPHA_GATE_ENABLED=false` and recreate the services so all hold the public-access configuration.
3. [ ] [Agent] Register a fresh operator-controlled account and verify sign-in/onboarding no longer requires alpha approval.
4. [ ] [Agent] Smoke dashboard access, invoice creation, share-link activation, signed-out invoice viewing, and invoice delivery with operator-controlled data.
5. [ ] [Agent] Verify all services report healthy and the watcher's run stamp advances after the restarts.
6. [ ] [Agent] Verify public invoice pages retain noindex while `/` and published articles are crawlable and canonicalize to the apex.
7. [ ] [Agent] Confirm no apex/`www` DNS record still targets Pages and record its retirement as the public serving target; preserve the content repo's source and Pages deployment configuration for recovery through DNS propagation.
8. [ ] [Agent] Record deployed tags, cutover time, URL/mail smoke verdicts, and any findings owned by M21.3.

## Halt and recovery

A wallet mismatch, broken core access, incorrect recipients/links, missing content routes, or unreliable payment processing stops the cutover. Use the verified [halt procedure](../ops/RUNNING_THE_SERVER.md#halt-procedure) and M21.1's deployment-specific recovery record. Recheck the target environment before destructive recovery. Gate access and hold mail while repairing; a fresh public signup makes a database restore a customer-data decision, so prefer configuration/image recovery where it suffices.

Bringing the stack up during rollback restarts stopped workers; stop queue/scheduler again until recovery is ready. Restore data only when the fault requires it and the impact has been assessed. DNS rollback alone cannot undo application writes, accepted callbacks, delivered mail, or on-chain payments.

## Exit Criteria

- [ ] The open beta is reachable under the apex with a valid certificate, verified renewal, and alpha approval disabled.
- [ ] The approved legal layer is live with the actual effective date, working links, and accurate analytics disclosure.
- [ ] Production services share the intended release/environment; wallet checks and watcher liveness pass.
- [ ] Production mail reaches intended recipients with apex links and working provider feedback; non-prod containment remains intact.
- [ ] The landing page replaces the placeholder, published content paths and indexing signals are preserved, and Pages serving is retired.
- [ ] Initial public-access smoke passes and recovery remains available; remaining rollout checks have explicit owners in M21.3.
