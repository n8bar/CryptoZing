# M21 Phase 2 Strategy — Deploy and Cutover

Status: Draft for review — execution not started.
Parent milestone: [`21_OB_DEPLOYMENT.md`](../milestones/21_OB_DEPLOYMENT.md)
Prerequisite: [M21.1 — Pre-deploy verification](21.1_PRE_DEPLOY_VERIFICATION.md) complete.
Next: [M21.3 — Rollout verification and sign-off](21.3_ROLLOUT_VERIFICATION_SIGNOFF.md)

Goal: open `https://cryptozing.app` with the approved legal layer, working mail, and preserved content URLs. [Shared references](../milestones/21_OB_DEPLOYMENT.md#execution-references) govern workflow and operations.

Keep cutover writes with one owner. A subagent can check public responses after each change without concurrent DNS, integration, or VPS edits.

## 1. [ ] Confirm the cutover inputs

1. [ ] Recheck Phase 1's app/site tags, configuration plan, analytics disposition, and legal approval against the release.
2. [ ] Refresh the verified backup from M21.1 §2 close to cutover.
   1. [ ] Confirm rollback tags/configuration and migration compatibility.
3. [ ] Confirm the prior hostname remains available for existing links and delayed callbacks.
4. [ ] [User] Accept the cutover window and go/no-go result.

## 2. [ ] Finalize legal publication and release artifacts

1. [ ] Replace policy effective-date placeholders with the actual publication date.
2. [ ] Resolve policy links and synchronize tracked drafts, app Markdown, and content-repo copies with approved wording and the analytics outcome.
3. [ ] Verify public policy access and placements against [M19.5](x19.5_LEGAL_LAYER.md).
4. [ ] Pin and verify the resulting app/site artifacts before public traffic.

## 3. [ ] Prepare apex serving and TLS

Normal apex traffic stays on Pages until §5.

1. [ ] Obtain and verify apex/redirect-host certificates using Phase 1's pre-DNS challenge plan.
2. [ ] Set `CZ_SERVER_NAME=cryptozing.app` and activate the prepared apex/retained-alpha nginx configuration and separate content container.
   1. [ ] Verify the current app/worker release remains in place until §4's migration step.
3. [ ] Verify HTTPS and HTTP/`www` redirects directly against the VPS with the intended hostnames and SNI.
4. [ ] Check content paths and assets through that route against Phase 1's baseline.
5. [ ] Configure renewal compatible with running nginx; public renewal proof follows in §5.

## 4. [ ] Activate app configuration with processing held

Keep the alpha gate enabled until the public-host smoke passes. Hold outbound mail and queue/scheduler processing through §5's DNS/callback checks.

1. [ ] Quiesce queue/scheduler processing and account for in-flight work.
2. [ ] Disable outbound mail in the running app.
3. [ ] Set `APP_URL=https://cryptozing.app` and confirm `APP_PUBLIC_URL` resolves to it.
4. [ ] Verify mainnet, production aliasing off, `MAIL_ALIAS_DOMAIN` cleared, and the verified donation configuration retained.
5. [ ] Run pending migrations once before starting the new app image, preserving existing mainnet data.
6. [ ] Recreate the app and serving services with the pinned release and updated environment.
   1. [ ] Recreate queue/scheduler containers without starting them; verify both remain stopped.
7. [ ] Run `wallet:check-config`; confirm the source-wallet comparison applies to the deployed keys.
8. [ ] Verify final app/legal/content routes directly against the VPS under the apex hostname before public traffic.
   1. [ ] Verify public-site crawlability/canonicals and retained alpha/staging/invoice noindex.

## 5. [ ] Switch DNS and restore delivery

1. [ ] Apply planned apex/`www` DNS changes, preserving mail and verification records.
   1. [ ] [Guided User] Complete required console actions if direct tooling is unavailable.
2. [ ] Check authoritative and independent recursive responses, including any AAAA record.
3. [ ] Verify apex HTTPS and HTTP/`www` redirects through normal DNS resolution.
4. [ ] Prove certificate renewal and its nginx reload hook through the public challenge route.
5. [ ] Retarget Mailgun's `delivered`, `temporary_fail`, and `permanent_fail` registrations to `https://cryptozing.app/webhooks/mailgun`.
   1. [ ] Verify the configured webhook signing key matches the account's.
   2. [ ] Verify callback reachability outside authentication and the alpha gate, with signature checking intact.
   3. [ ] Verify pre-cutover event continuity through the prepared old-host handling.
6. [ ] Restore outbound mail and recreate app, queue, and scheduler with the final environment before resuming processing.
   1. [ ] Verify the prepared release, public host, wallet network, and mail settings agree across all three.
   2. [ ] Start queue/scheduler processing and confirm those runtime values.
7. [ ] Send an operator-addressed invoice and issuer-reviewed paid receipt; verify apex links, receipt of mail, and callback-driven delivery state. Retain these messages/rows for M21.3 §3.

## 6. [ ] Open access and complete the cutover smoke

1. [ ] Verify the apex landing/legal/content routes through public DNS while app access remains gated.
2. [ ] Set `ALPHA_GATE_ENABLED=false` and recreate the app, queue, and scheduler.
3. [ ] Register an operator-controlled account and verify sign-in/onboarding without alpha approval.
4. [ ] Smoke dashboard access and invoice creation.
   1. [ ] Activate its share link and verify signed-out viewing.
   2. [ ] Verify delivery to the operator-controlled client.
5. [ ] Run the [service and watcher health checks](../ops/RUNNING_THE_SERVER.md#reading-health-honestly) after the restarts.
6. [ ] Confirm no apex/`www` DNS record targets Pages; retain its deployment configuration for recovery through propagation.
7. [ ] Hand M21.3 deployed tags, cutover time, URL/mail verdicts, and remaining findings.

## Halt and recovery

Wallet mismatches, broken core access, incorrect recipients/links, missing content routes, or unreliable payment processing stop cutover. Use the [halt procedure](../ops/RUNNING_THE_SERVER.md#halt-procedure) and M21.1's DNS/hostname/webhook recovery record; gate public access during repair. After public signups, assess customer-data loss before any restore and prefer configuration/image recovery where sufficient.

## Exit Criteria

- [ ] Public access, TLS/renewal, legal publication, and preserved content routes pass.
- [ ] Release/configuration, wallets, watcher, and production delivery pass the cutover checks.
- [ ] Recovery remains available and rollout verification is handed to M21.3.
