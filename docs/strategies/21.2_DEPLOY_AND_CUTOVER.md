# M21 Phase 2 — Switch to the Apex and Open Beta

Status: Draft for review — execution not started.
Parent: [M21](../milestones/21_OB_DEPLOYMENT.md)
Prerequisite: [M21.1](21.1_PRE_DEPLOY_VERIFICATION.md) complete.
Next: [M21.3 — Verify and sign off](21.3_ROLLOUT_VERIFICATION_SIGNOFF.md)

Goal: turn the existing alpha deployment into the public beta and retire its old hostname.

Cutover is serial. Public-response checks can be delegated after each change; production configuration has one owner. Normal processing continues through DNS preparation. The mail circuit breaker is not a pause mechanism: it records invoice-send attempts as skipped.

## 1. [ ] Prepare the cutover and publication

1. [ ] [User] Accept the cutover window and Phase 1's old-link disposition.
2. [ ] Capture the current app/site image digests and nginx/env/DNS/webhook configuration in local recovery storage.
3. [ ] Take a fresh encrypted database backup and verify it decrypts using the [backup procedure](../ops/RUNNING_THE_SERVER.md#backups).
4. [ ] Put the actual publication date in the reviewed legal copies and the sitemap's root `lastmod`.
   1. [ ] Publish the resulting app/site artifacts and record their immutable release IDs.
   2. [ ] Confirm Phase 1's tested configuration still applies.

## 2. [ ] Make the apex ready on the existing stack

Normal apex traffic still goes to Pages; alpha continues serving the existing app.

1. [ ] Issue and verify the apex/`www` certificate through the prepared DNS challenge.
2. [ ] Install the prepared transition routing and selected app/site release on the existing stack.
   1. [ ] Use the [existing deploy path](../../scripts/deploy.sh) with Phase 1's explicit site-image selection; migrations run before app services switch.
   2. [ ] Keep `APP_URL`/`APP_PUBLIC_URL` on alpha and the approval gate enabled at this stage; retain existing wallet and mail settings.
3. [ ] Test apex HTTPS and HTTP/`www` redirects directly against the VPS using the intended hostnames and SNI.
4. [ ] Verify the landing page, published policies, and representative article/asset routes through that direct route.
5. [ ] Verify alpha still serves the running app and its callbacks during the transition.

## 3. [ ] Move apex traffic

1. [ ] Point apex/`www` DNS at the VPS, preserving mail and verification records.
   1. [ ] [Guided User] Complete required DNS-console changes.
2. [ ] Verify authoritative and independent recursive responses, including any AAAA record, and allow the previous TTL to clear.
3. [ ] Verify HTTPS, canonical redirects, landing/policy pages, and representative content through normal public DNS.
4. [ ] Apply the new certificate's prepared unattended-renewal settings to the existing certificate infrastructure.
   1. [ ] Test renewal and nginx reload for the apex while nginx owns port 80.
5. [ ] Confirm Pages is no longer the apex DNS target; retain its source/build configuration for recovery.
   1. [ ] Activate the prepared VPS content-publishing procedure.
   2. [ ] Disable Pages-triggered IndexNow notifications.
   3. [ ] Update [CONTENT_PLAN.md](../CONTENT_PLAN.md) to match the new public serving target.

## 4. [ ] Switch generated links and callbacks

1. [ ] Retarget Mailgun's `delivered`, `temporary_fail`, and `permanent_fail` registrations to `https://cryptozing.app/webhooks/mailgun`.
   1. [ ] Verify the apex callback accepts valid provider events without authentication/approval-gate interference and retains signature validation.
2. [ ] Set `APP_URL=https://cryptozing.app`, `APP_PUBLIC_URL` to the same value, and `CZ_SERVER_NAME=cryptozing.app`.
   1. [ ] Recreate app, queue, scheduler, and affected nginx configuration; verify each holds its intended values. Keep the approval gate enabled for the smoke.
3. [ ] Sign in with an existing operator account on the apex and verify access to its existing invoices.
4. [ ] Send one operator-addressed invoice with the normal mail settings.
   1. [ ] Verify apex links and the corresponding provider callback/delivery state; retain the message for Phase 3's inbox check.
5. [ ] Confirm Phase 1's old-link disposition is satisfied, including any required replacements.
6. [ ] Resolve outstanding old-host callbacks through the prepared completion/reconciliation procedure.

## 5. [ ] Retire alpha and open access

1. [ ] Remove alpha's DNS records and activate the prepared apex-only nginx configuration.
   1. [ ] Verify alpha no longer reaches the app, including wildcard DNS and cached-host requests.
   2. [ ] Retire alpha-only certificate/renewal entries after confirming the apex does not depend on them.
2. [ ] Set `ALPHA_GATE_ENABLED=false` and recreate app, queue, and scheduler.
3. [ ] Verify the apex remains reachable and the running services hold the final public configuration.
4. [ ] Hand Phase 3 the deployed IDs, cutover time, mail-test reference, and any remaining findings.

## Backout

A failed cutover check stops progression. Before opening access, retain the approval gate and restore the affected image/configuration/DNS values from §1. Do not reset the database for a hostname failure. Cached DNS may still reach the VPS after reversal, so keep it serving valid routes during recovery.

After opening, re-enable approval if the release must be withdrawn; preserve any newly created customer data during recovery.

For an actual payment/data incident, use the [halt procedure](../ops/RUNNING_THE_SERVER.md#halt-procedure); it is not the normal cutover sequence.

## Exit Criteria

- [ ] The same deployment serves the apex with valid TLS, working generated links/callbacks, and public access enabled.
- [ ] Alpha's hostname is retired and Pages is no longer the public serving target.
- [ ] Publication is live, recovery remains available, and Phase 3 has the cutover evidence.
