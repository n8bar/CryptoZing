# MS20 Phase 1 Strategy — Alpha Access Gate

Status: Complete.
Parent milestone doc: [`docs/milestones/x20_MAINNET_CUTOVER_ALPHA_GATE.md`](../milestones/x20_MAINNET_CUTOVER_ALPHA_GATE.md)

**Goal:** Registration stays open and untouched; new accounts land pending and cannot log in until approved from the support dashboard. Independent of mainnet — ships ahead of the hosting and wallet phases.

## 1. [x] Approval state

1. [x] Add nullable `approved_at` to `users` — non-null means approved, matching the timestamp-as-flag pattern already used for 2FA.
   1. [x] Backfill existing users as approved in the same migration, so current accounts don't lock themselves out on deploy.
2. [x] Add `User::isApproved()` plus pending and approved query scopes. Factory defaults approved; `pending()` state added.
3. [x] Add `config/alpha.php` with an env-overridable `gate_enabled`, default on. `ALPHA_GATE_ENABLED`.
4. [x] Read that flag through one accessor in both registration and login, so the two halves can't disagree. `AlphaGate::enabled()` / `AlphaGate::blocks()`; shared refusal copy in `AlphaGate::REFUSAL_MESSAGE`.

## 2. [x] Registration

1. [x] Create the account pending in `RegisteredUserController::store`, dropping the `Auth::login()` call. Gate off auto-approves and logs in as before.
2. [x] Move the getting-started auto-show to first login after approval — it can no longer fire at register. Login path already fires it via `RoutesAuthenticatedUser`.
3. [x] Build the awaiting-approval page.
   1. [x] Guest-safe route and view, reachable without a session. `approval.pending` → `/awaiting-approval`.
   2. [x] Copy: the account exists, access is granted manually, mail arrives on approval.

## 3. [x] Login gate

1. [x] Refuse pending accounts in `AuthenticatedSessionController::store`, immediately after the credential check and ahead of the 2FA divert — no session, and no second-factor code sent to an account that can't get in either way.
2. [x] Re-check in `TwoFactorChallengeController::store` before login completes, covering an account revoked while holding a pending challenge. Also guards `resend()` — same window, same no-code rationale.
3. [x] Clear the half-authenticated session state when that re-check refuses. Challenge code/attempt state cleared too.
4. [x] Return to login on refusal with an awaiting-approval message.
5. [x] Preserve the entered email through the refusal per [`docs/UX_GUARDRAILS.md`](../UX_GUARDRAILS.md).

## 4. [x] Support dashboard approvals

1. [x] Add a pending approvals panel at `/support` inside the existing `EnsureSupportAgent` group, listing pending accounts with name, email, and registered-at, paginated like the issuer list. Own `pending_page` paginator.
2. [x] Add the approve action: set `approved_at` and fire the approval mail (§5). `support.approvals.approve`.
3. [x] Add the revoke action, clearing `approved_at`. `support.approvals.revoke`; no UI surface — spec'd panel lists pending only.
   1. [x] Invalidate the account's sessions so access drops immediately rather than at next login. Done via `EnsureApprovedUser` middleware (web group): revoked session drops on its next request under any session driver, rather than by deleting DB session rows.
   2. [x] Reject a self-revoke — it locks the operator out of the only surface that can undo it.
4. [x] Make the Support UI's LOOK UP button not require exact matches. Email substring match; SQL wildcards treated as literals; results capped at 10 with a narrow-the-search note.

## 5. [x] Approval notification

1. [x] Build `AccountApprovedMail` on the existing branded mail surface, queued like the other mailables.
2. [x] Copy: approved, with a login link. Link built from `app.public_url`.

## 6. [x] Tests

1. [x] Registration creates a pending account, establishes no session, and lands on the awaiting-approval page.
2. [x] Pending account with correct credentials is refused; no session, message shown.
3. [x] Account with 2FA enabled is refused before the challenge, with no code sent.
4. [x] Account revoked while holding a pending challenge is refused when it submits a valid code.
5. [x] Approve, then log in successfully.
6. [x] Revoke, then find the live session unauthenticated on its next request.
7. [x] Approvals panel and both actions are `EnsureSupportAgent`-gated; a non-agent gets 403. Panel gating rides `/support`, already covered by `SupportAccessTest`.
8. [x] Self-revoke is rejected.
9. [x] Approval mail fires on approve and not on revoke.
10. [x] Gate disabled by config → registration logs in as before. Also: gate off admits a pending login; gate-off registration auto-approves.
11. [x] Migration backfill leaves pre-existing users approved.

## 8. [x] Account ban (gate-independent)

1. [x] Nullable `banned_at` on users — same timestamp-as-flag pattern; blocks regardless of `ALPHA_GATE_ENABLED`.
2. [x] Refuse banned accounts at login, 2FA challenge (store + resend), and per-request via the existing middleware (renamed `EnsureAccountActive`). One decision point: `AlphaGate::refusal()` — ban wins over gate.
3. [x] Distinct copy — no approval promise; neutral "this account has been disabled." `AlphaGate::BANNED_MESSAGE`.
4. [x] Support panel: account lookup by email showing state, with Ban/Unban — doubles as the revoke surface. Self-ban rejected. Lookup card shows Approve/Revoke/Ban/Unban per state; unban restores prior approval state.
5. [x] No mail on ban/unban.
6. [x] Tests mirroring §6: gate on and off, mid-challenge ban, live-session drop, agent gating, self-ban. `AccountBanTest`, 10 tests.
7. [x] Test Banning/Unbanning
	1. [x] Ban an account.
	2. [x] Attempt to log in with banned account and verify rejection and message.
	3. [x] Unban the account.
	4. [x] Verify login experience is restored.

## Exit Criteria

- [x] New registrations create a pending account; registration UX unchanged and fully functional.
- [x] Pending accounts cannot authenticate; login is blocked with clear messaging until approval, and the check interoperates with password auth and 2FA.
- [x] Support dashboard shows a pending approvals list with approve and revoke actions, gated by `EnsureSupportAgent`.
- [x] Pending → approved → login transition covered by migration and feature tests.
- [x] Approval mail delivered on approve.
