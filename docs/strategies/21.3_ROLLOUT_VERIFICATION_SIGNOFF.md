# M21 Phase 3 Strategy — Post-deploy Verification and Rollout Sign-off

Status: Draft for review — execution not started.
Drafted: 2026-09-05.
Parent milestone: [`21_OB_DEPLOYMENT.md`](../milestones/21_OB_DEPLOYMENT.md)
Prerequisite: [`21.2_DEPLOY_AND_CUTOVER.md`](21.2_DEPLOY_AND_CUTOVER.md) complete.

Goal: verify the public deployment's user journeys and operating state, resolve rollout findings, and obtain operator acceptance before closing M21.

`Agent` drives verification and fixes; `Guided User` handles webmaster/provider account checks requiring coaching; `User` performs wallet actions, eyes-on review, and final sign-off. Use operator-controlled accounts, clients, and inboxes for smoke tests. M20 already proved live invoice/donation settlement, correction handling, and halt/restore; this phase checks the cutover's effect on that baseline.

Safe parallel work: after §1, delegate read-only public-site/SEO checks (§5) separately from app/mail verification (§§2–3). A self-host/runbook sidecar may compare §6's docs with the release. One Agent owns production writes; findings return to that Agent for integration and re-verification.

## 1. [ ] Verify deployment health

1. [ ] [Agent] Check per-service Compose health using both production Compose files and confirm the running app/site tags match the cutover record.
2. [ ] [Agent] Check for pending migrations and confirm app, queue, and scheduler report the intended production/mainnet/public-host configuration.
3. [ ] [Agent] Observe the watcher stamp advance across successive scheduled runs; verify the support dashboard's stale tile agrees.
4. [ ] [Agent] Inspect queue failures and application/mail/watcher logs for cutover errors; compare worker restart counts with the expected hourly recycle.
5. [ ] [Agent] Verify the first backup and off-box pull after cutover succeed, with the established schema-only exclusions intact.

## 2. [ ] Verify issuer, payer, and legal journeys

1. [ ] [Agent] Complete the new-account journey without alpha approval: registration, applicable account verification, sign-in, and wallet onboarding.
2. [ ] [Agent] Verify existing-account access and the configured email/TOTP 2FA paths still work on the apex.
3. [ ] [Agent] Create an invoice with an operator-controlled client and confirm the address belongs to the expected invoice wallet.
4. [ ] [Agent] Enable its share link and open it signed out; verify displayed USD/BTC amounts, payment request/QR, status, and noindex against the relevant specs.
5. [ ] [Agent] Check a second issuer cannot access the first issuer's invoices or clients; verify denied responses reveal no private details.
6. [ ] [Agent] Exercise representative pre-cutover links under the old-host handling, including signed links, and confirm fresh links use the apex.
7. [ ] [Agent] Verify signup, wallet, invoice-screen/print, and policy/footer placements against [M19.5](x19.5_LEGAL_LAYER.md).
8. [ ] [User] Read the live landing page, policy pages, disclaimers, and invoice screen/print in both themes and at mobile width; report any blocking rendering or navigation issue.
9. [ ] [Agent] Recheck any changed UX against [`UX_GUARDRAILS.md`](../UX_GUARDRAILS.md), including focus, keyboard operation, contrast, and preserved input.

## 3. [ ] Verify payment integrity and production mail

1. [ ] [Agent] Compare existing invoice/payment and donation addresses, satoshis, blocks, and confirmation times with the chain.
   1. [ ] Verify payment USD snapshots against their stored rates and settlement times against the [confirmation/tolerance rules](../specs/PARTIAL_PAYMENTS+CONFIRMATIONS.md).
2. [ ] [Agent] Confirm donation transactions remain outside invoice payment records and allocation stays independent.
3. [ ] [Agent] Assess whether the deployed delta or a failed check calls for another controlled live invoice/donation payment beyond M20's completed proof.
   1. [ ] For a required payment, identify the failed or changed behavior and prepare a small operator-owned scenario after wallet validation passes.
   2. [ ] [User] Send any required funds from the source wallet; keep signing material outside the app and repo.
   3. [ ] [Agent] Verify pending detection, configured confirmation gating, final attribution, and relevant notices for that scenario.
   4. [ ] Record the resulting verdict, or record why M20's existing live proof plus the current integrity checks are sufficient when no repeat is needed.
4. [ ] [Agent] Deliver an invoice email and send an eligible paid receipt through the issuer's reviewed receipt action; verify recipients are not aliased.
5. [ ] [Agent] Confirm provider delivery events settle the corresponding rows truthfully, without duplicate sends or stranded queued/sending state.
6. [ ] [Agent] Verify every message link points at the intended apex surface and works from a signed-out browser where appropriate.
7. [ ] [User] Inspect the received invoice and receipt in a real mail client for sender, rendering, and SPF/DKIM/DMARC pass with the expected alignment.
8. [ ] [User] Confirm the sampled invoice/donation receive addresses and any new payments appear as expected in the source wallets.

## 4. [ ] Discharge the conditional mail-stress carry

1. [ ] [Agent] Recheck M21.1 §5's [#81](https://github.com/n8bar/CryptoZing/issues/81) disposition against the deployed mailer and available quota.
2. [ ] [Agent] For a triggered rerun, execute the applicable deferred [M19.1 §6 scenarios](x19.1_NOTIFICATION_COVERAGE_AUDIT.md#6-stress-readiness-check-best-effort) with contained recipients and an isolated workload where failure injection is needed.
3. [ ] [Agent] Record completed scenario verdicts and any still-unexercised limits. If the trigger remains absent, retain the explicit upgrade/switch trigger and named future owner rather than claiming stress testing passed.

## 5. [ ] Verify public discovery and analytics

1. [ ] [Agent] Compare the apex landing page, every published article URL, and required assets with the M21.1 baseline; resolve missing paths or changed redirects.
2. [ ] [Agent] Verify HTTPS/non-`www` redirects, canonical tags, social metadata, structured data, robots, and sitemap behavior on the live deployment.
3. [ ] [Agent] Confirm published apex pages have no inherited blanket noindex, while alpha/staging and public invoice surfaces retain their intended exclusion.
4. [ ] [Guided User] Verify Search Console and Bing ownership still holds and inspect the live root and sitemap for fetch/canonical regressions. Record delayed indexing feedback separately from actual fetch failures.
5. [ ] [Agent] Verify a marketing page reaches the analytics endpoint selected in M21.1 §6 and the live Privacy Policy describes that actual setup.
6. [ ] [Agent] Confirm signed-in app, invoice, and staging pages send no analytics events and the migration has not introduced duplicate tracking.
7. [ ] [Agent] Leave discovery observations for [M22](../milestones/22_SEO_MARKETING.md); the broader SEO/marketing program remains scoped at that milestone's kickoff.

## 6. [ ] Verify operations and resolve rollout findings

1. [ ] [Agent] Walk the non-destructive operating checks in [`RUNNING_THE_SERVER.md`](../ops/RUNNING_THE_SERVER.md) against the live server and correct inaccurate or insufficient guidance.
2. [ ] [Agent] Confirm backup/decryption access, rollback tags, and the halt instructions still apply to the public-host configuration using M21.1's verified restore and M20's completed halt rehearsal.
3. [ ] [Agent] File rollout findings as GitHub Issues with a named acceptance home; fix launch-blocking issues and repeat the affected checks.
4. [ ] [Agent] Review any proposed deferral against the phase exit criteria; retain explicit ownership and acceptance rather than treating issue filing as resolution.
5. [ ] [Agent] Check whether real customer data now exists and update AGENTS.md's data-hygiene note accordingly.

## 7. [ ] Obtain sign-off and close the milestone

1. [ ] [Agent] Present the deployed tags and concise verdicts for access, wallets/payments, mail, public URLs/indexing, legal publication, self-hosting, and operations; include the analytics and #81 dispositions.
2. [ ] [User] Confirm the public deployment is fit for open beta after reviewing the evidence and any accepted deferrals.
3. [ ] [Agent] Complete the milestone's content-promises check against the shipped result; update the catalog for any new commitment.
4. [ ] [Agent] Check off the completed phase and milestone at their owning doc depths, then x-prefix completed milestone/strategy filenames and retarget inbound links in the same closing commit.
5. [ ] [Agent] Synchronize PLAN, README, AGENTS.md, and CHANGELOG with the closed milestone and M22 handoff; keep dates tied to `milestones.ics` and do not infer a schedule change from completion.

## Exit Criteria

- [ ] Public account/invoice flows and existing-link compatibility pass, with ownership boundaries intact.
- [ ] Payment records remain correct; any required live revalidation and issuer-reviewed receipt delivery pass.
- [ ] Real inbox mail, provider feedback, public hosts, and non-prod containment are verified.
- [ ] Legal surfaces, preserved content URLs, discovery signals, and analytics disclosure match the deployed result.
- [ ] Services, watcher, backups, and operating guidance pass verification; rollout findings have an accepted disposition with no unresolved launch blocker.
- [ ] The operator has signed off and the milestone closeout/handoff is committed with canonical docs synchronized.
