# MS20 Phase 4 Strategy — Mainnet Environment & Wallets

Status: Complete.
Parent milestone doc: [`docs/milestones/20_MAINNET_CUTOVER_ALPHA_GATE.md`](../milestones/20_MAINNET_CUTOVER_ALPHA_GATE.md)

**Goal:** Bring the deployed box onto a clean mainnet baseline and configure it for the private window, with two separate watch-only xpubs onboarded and their derived addresses verified against the source wallets before any funds move. Phase 5 sends the first real payment.

## 1. [x] Operator wallets

Section 1 gates the rest of the phase and only the operator can do it.

1. [x] [User] Create the mainnet invoice wallet and export its Taproot (BIP86) account key — Phase 3 must land first so onboarding accepts it.
2. [x] [User] Create a separate mainnet donation wallet and export its Taproot account key.
3. [x] [User] Confirm the two xpubs are different keys, not two accounts under one — a shared key collides derivation chains and destroys attribution, which is the MS14 failure. Confirmed: separate, distinct BIP39 seeds.
4. [x] [User] Keep both seeds off the box, out of the repo, and out of any password field in the app. Confirmed: offline primary backup; operator-side encrypted cloud copy only.

## 2. [x] Clean mainnet baseline

Flipping the network on top of testnet rows strands them: addresses derived on one network never match the other, and the watcher would be reconciling against a chain those rows were never on. The app holds only seed and test data, so the baseline starts empty.

1. [x] Drop the testnet database and bring up an empty one.
2. [x] Run migrations against it with no seeders.
3. [x] Confirm nothing survived: no wallet accounts, key cursors, invoices, payments, or donation rows. Zero rows across users, wallet_settings, user_wallet_accounts, wallet_key_cursors, invoices, invoice_payments, donations, clients.
4. [x] Create the operator account fresh, and approve it through the Phase 1 gate. `cz.support@cryptozing.app` (user 1), bootstrapped via tinker — no approved approver exists on a fresh DB; doubles as the support agent account, `SUPPORT_AGENT_EMAILS` updated to match.

## 4. [x] Onboard and verify the keys

1. [x] Onboard the invoice xpub at `/wallet/settings`.
2. [x] Derive the first several invoice addresses in the app. Indexes 0–4, static derivation, cursors untouched.
3. [x] [User] Compare them against the same derivation path in the source wallet, and stop the phase on any mismatch.
   1. [x] [User] In the invoice wallet app, list the first five receive addresses (path `m/86'/0'/0'/0/0`–`0/4`).
   2. [x] [Agent] Compare index-by-index against the §4.2 list. Diffed against a fresh derivation off the box, not §4.2's transcript.
   3. [x] [Agent] Report the verdict; any mismatch stops the phase. All five match, index for index. Addresses stay out of tracked docs — this repo is public and they are the operator's live receive chain.
4. [x] Confirm the app does not flag the key as an unsupported wallet configuration. mainnet/bip86, `unsupported_configuration_active=false`.
5. [x] Derive a donation address and compare it against the donation wallet the same way.
   1. [x] Derive indexes 0–2 from the configured donation key. Taproot, cursors untouched.
   2. [x] [User] Compare them against the donation wallet's first receive addresses; any mismatch stops the phase. Indexes 0–1 match.
6. [x] Confirm the invoice and donation chains advance independently — one key's cursor must not move when the other allocates. Allocated one of each in a rolled-back transaction: neither chain moved the other, both advanced their own, addresses differ.

## 5. [x] Watch-only audit

1. [x] Search the box, the published image, and the repo for anything seed-shaped or key-shaped. Box and logs clean, no `.env` baked into the image; the only matches anywhere are published BIP32/BIP39 test vectors — in the `bip32` library's README and in tracked rejection fixtures.
2. [x] Confirm the database holds public keys only. Full dump carries no plaintext private material; the one key column holds an `xpub`, encrypted at rest.
3. [x] Confirm no app flow asks for or accepts a private key. Acceptance is allowlisted (`xpub|zpub` / `tpub|vpub`) across all three key-taking requests, so private material cannot be stored.
   1. [x] Land [#150](https://github.com/n8bar/CryptoZing/pull/150) — rejected keys were flashed to the session in plaintext and echoed back into the form. Merged; the scrub fires only on a positive signing-material hit, so an ordinary typo still repopulates.
   2. [x] Fix [#148](https://github.com/n8bar/CryptoZing/issues/148) — the seed-phrase warning never fires from the browser. Closed by #150: mnemonics segment against the vendored BIP39 wordlist, so the concatenated form the browser submits trips the seed-specific warning.
   3. [x] Fix [#149](https://github.com/n8bar/CryptoZing/issues/149) — `DONATION_WALLET_XPUB` is not validated where it is read. `DonationKey` applies onboarding's network-aware allowlist at the read point, so the donate routes and the footer link register only for a usable key ([#152](https://github.com/n8bar/CryptoZing/pull/152)).
   4. [x] Fix [#146](https://github.com/n8bar/CryptoZing/issues/146) — the donation key is never checked against the onboarded invoice key; same read point as §5.3.3. `wallet:check-config` parses both sides, so a bare key and that key inside a `tr()` descriptor register as one wallet; on the rollout checklist.
   5. [x] Fix [#151](https://github.com/n8bar/CryptoZing/issues/151) — signing material crosses the wire on the live-preview call before the server ever sees it. Paste is cancelled before the phrase reaches the field, and every path to the preview endpoint runs the guard first; the server check stays the authority.
