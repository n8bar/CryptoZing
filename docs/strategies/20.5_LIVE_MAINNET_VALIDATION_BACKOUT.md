# MS20 Phase 5 Strategy — Live Mainnet Validation & Backout

Status: In Progress.
Parent milestone doc: [`docs/milestones/20_MAINNET_CUTOVER_ALPHA_GATE.md`](../milestones/20_MAINNET_CUTOVER_ALPHA_GATE.md)
Supporting ops doc: [`docs/ops/OB_ROLLOUT_CHECKLIST.md`](../ops/OB_ROLLOUT_CHECKLIST.md)

**Goal:** Prove the payment pipeline with real self-sent mainnet money — an invoice and a donation, each end to end — exercise the correction tooling against live data, and leave behind a cutover runbook and a halt procedure that MS21 executes.

Real funds move in this phase. Self-sending means the coins come back and the fee is the only real cost, but none of it is reversible by anything in §5.

## 1. [ ] Real invoice, end to end

1. [ ] Issue a small invoice — a few dollars is far above dust, so the amount is about limiting exposure, not about the protocol.
2. [ ] Confirm the derived address belongs to the operator invoice key, not the donation key.
3. [ ] [User] Send the payment from the operator wallet at a low fee rate with RBF enabled.
   1. [ ] The slow confirmation is deliberate: it holds the transaction unconfirmed long enough to actually watch the mempool step.
   2. [ ] Bump the fee if it stalls past patience, and confirm the watcher follows the replacement rather than tracking a transaction that no longer exists.
4. [ ] Confirm the watcher detects it unconfirmed, in the mempool.
5. [ ] Confirm it settles at the configured confirmation count and not before.
6. [ ] Confirm the invoice moves to paid on its own, with no manual nudge.
7. [ ] Confirm the recorded BTC amount and its USD snapshot match what was actually sent.
8. [ ] Confirm the paid receipt sends.

## 2. [ ] Real donation, end to end

1. [ ] Allocate a donation address from `/donate`.
2. [ ] Confirm it derives from the donation key, on a chain the invoice key never touches.
3. [ ] [User] Send the donation from a wallet that isn't the invoice wallet, funded by the §1 change so the phase costs two fees in total.
4. [ ] Confirm it lands on the donation row and is never recorded as an invoice payment.
5. [ ] Confirm the donor receipt sends.
6. [ ] Confirm the operator notification reaches `DONATION_NOTIFY_EMAIL`.

## 3. [ ] Mail sanity on mainnet

1. [ ] Register the Mailgun webhook against the private hostname for `delivered`, `failed`, and `permanent_fail`.
2. [ ] Set `MAILGUN_WEBHOOK_SIGNING_KEY` from the dashboard.
3. [ ] Confirm delivery status flows back and lands on the delivery log rather than staying queued.
4. [ ] Confirm every link in the sent mail resolves to `APP_PUBLIC_URL` and not to localhost or the apex.
5. [ ] Confirm DKIM, SPF, and DMARC all pass for the sending domain.
6. [ ] [User] Read the invoice and receipt mail in a real client and judge headers, sender, and rendering.

## 4. [ ] Correction tooling against live data

This is the first chance to run the MS14 tooling against real on-chain conditions rather than fixtures.

1. [ ] Construct a wrong-attribution scenario on the live data — record-level, against the §1 payment and a second invoice.
2. [ ] Ignore the misattributed payment and confirm the invoice total corrects.
3. [ ] Restore it and confirm the total returns.
4. [ ] Reattribute it to the correct invoice and confirm both invoices land right.
5. [ ] Confirm the audit trail shows who did what, and when.
6. [ ] File any gap found as a GitHub Issue.

## 5. [ ] Runbook and halt procedure

1. [ ] Write the cutover runbook from what this phase actually did, not from what we planned.
   1. [ ] Environment flips, in the order they have to happen.
   2. [ ] Wallet validation before funds move.
   3. [ ] Mail sanity checks.
   4. [ ] Post-deploy checks and who signs them off.
2. [ ] Write the halt procedure for a cutover going wrong.
   1. [ ] Stop the watcher and queue worker so nothing auto-acts on bad state.
   2. [ ] Set `MAIL_OUTBOUND_ENABLED=false` so no mail goes out on a wrong assumption.
   3. [ ] Roll back to the previous image tag.
   4. [ ] Restore the database from the most recent verified backup.
   5. [ ] State plainly what a halt cannot undo: coins already sent, and mail already delivered.
3. [ ] Prove the halt procedure by running it, then bring the box back up.
4. [ ] Fold both into [`docs/ops/OB_ROLLOUT_CHECKLIST.md`](../ops/OB_ROLLOUT_CHECKLIST.md), which is what MS21 executes.

## 6. [ ] Verification

1. [ ] [Agent] Walk the invoice from derivation to receipt in the delivery log and payment ledger, and confirm the record matches the chain.
2. [ ] [Agent] Confirm the donation never appears in invoice payment queries.
3. [ ] [Agent] Confirm the invoice and donation key cursors moved independently of each other.
4. [ ] [Agent] Confirm the watcher-stale signal on the support dashboard stayed quiet through the run.
5. [ ] [User] Confirm both payments appear as expected in your source wallets.
6. [ ] [User] Sign off that the runbook is followable by someone who wasn't here when it was written.

## Exit Criteria

- [ ] Real self-sent mainnet invoice validated end to end: derived → paid → detected → confirmed → marked paid → receipt mail.
- [ ] Real self-sent mainnet donation validated end to end: derived → paid → recorded on the donation row (never as an invoice) → receipt → operator notification mail.
- [ ] MS14 correction tooling exercised against a wrong-attribution scenario on live mainnet data; every Issue it raised is closed or deferred with a stated reason.
- [ ] Watcher follows an RBF replacement rather than tracking a transaction that no longer exists.
- [ ] Mail sanity on mainnet: correct `APP_PUBLIC_URL` links and headers; DKIM, SPF, and DMARC confirmed; delivery status flowing back through the webhook.
- [ ] Cutover runbook complete and proven by execution.
- [ ] Halt procedure proven by execution, with its limits stated.
