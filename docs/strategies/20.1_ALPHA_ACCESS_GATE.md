# MS20 Phase 1 Strategy — Alpha Access Gate

Status: Not Started.
Parent milestone doc: [`docs/milestones/20_MAINNET_CUTOVER_ALPHA_GATE.md`](../milestones/20_MAINNET_CUTOVER_ALPHA_GATE.md)

**Goal:** Registration stays open and untouched; new accounts land pending and cannot log in until approved from the support dashboard. Independent of mainnet — ships ahead of the hosting and wallet phases.

## 1. [ ] Approval state

1. [ ] Add nullable `approved_at` to `users` — non-null means approved, matching the timestamp-as-flag pattern already used for 2FA.
   1. [ ] Backfill existing users as approved in the same migration, so current accounts don't lock themselves out on deploy.
2. [ ] Add `User::isApproved()` plus pending and approved query scopes.
3. [ ] Add `config/alpha.php` with an env-overridable `gate_enabled`, default on.
4. [ ] Read that flag through one accessor in both registration and login, so the two halves can't disagree.

## 2. [ ] Registration

1. [ ] Create the account pending in `RegisteredUserController::store`, dropping the `Auth::login()` call.
2. [ ] Move the getting-started auto-show to first login after approval — it can no longer fire at register.
3. [ ] Build the awaiting-approval page.
   1. [ ] Guest-safe route and view, reachable without a session.
   2. [ ] Copy: the account exists, access is granted manually, mail arrives on approval.

## 3. [ ] Login gate

1. [ ] Refuse pending accounts in `AuthenticatedSessionController::store`, immediately after the credential check and ahead of the 2FA divert — no session, and no second-factor code sent to an account that can't get in either way.
2. [ ] Re-check in `TwoFactorChallengeController::store` before login completes, covering an account revoked while holding a pending challenge.
3. [ ] Clear the half-authenticated session state when that re-check refuses.
4. [ ] Return to login on refusal with an awaiting-approval message.
5. [ ] Preserve the entered email through the refusal per [`docs/UX_GUARDRAILS.md`](../UX_GUARDRAILS.md).

## 4. [ ] Support dashboard approvals

1. [ ] Add a pending approvals panel at `/support` inside the existing `EnsureSupportAgent` group, listing pending accounts with name, email, and registered-at, paginated like the issuer list.
2. [ ] Add the approve action: set `approved_at` and fire the approval mail (§5).
3. [ ] Add the revoke action, clearing `approved_at`.
   1. [ ] Invalidate the account's sessions so access drops immediately rather than at next login.
   2. [ ] Reject a self-revoke — it locks the operator out of the only surface that can undo it.

## 5. [ ] Approval notification

1. [ ] Build `AccountApprovedMail` on the existing branded mail surface, queued like the other mailables.
2. [ ] Copy: approved, with a login link.

## 6. [ ] Tests

1. [ ] Registration creates a pending account, establishes no session, and lands on the awaiting-approval page.
2. [ ] Pending account with correct credentials is refused; no session, message shown.
3. [ ] Account with 2FA enabled is refused before the challenge, with no code sent.
4. [ ] Account revoked while holding a pending challenge is refused when it submits a valid code.
5. [ ] Approve, then log in successfully.
6. [ ] Revoke, then find the live session unauthenticated on its next request.
7. [ ] Approvals panel and both actions are `EnsureSupportAgent`-gated; a non-agent gets 403.
8. [ ] Self-revoke is rejected.
9. [ ] Approval mail fires on approve and not on revoke.
10. [ ] Gate disabled by config → registration logs in as before.
11. [ ] Migration backfill leaves pre-existing users approved.

## 7. [ ] Verification

1. [ ] [Agent] Register a fresh account in the running stack.
   1. [ ] Confirm the pending row, no session, and the awaiting-approval page.
   2. [ ] Confirm login is refused and no code is sent for a 2FA-enabled pending account.
2. [ ] [Agent] Approve from `/support` and confirm login succeeds.
3. [ ] [Agent] Revoke and confirm the live session is gone on its next request.
4. [ ] [User] Receive the approval mail in a real inbox and confirm its link lands on login.
5. [ ] [User] Eyeball the awaiting-approval page and the login refusal message.

## Exit Criteria

- [ ] New registrations create a pending account; registration UX unchanged and fully functional.
- [ ] Pending accounts cannot authenticate; login is blocked with clear messaging until approval, and the check interoperates with password auth and 2FA.
- [ ] Support dashboard shows a pending approvals list with approve and revoke actions, gated by `EnsureSupportAgent`.
- [ ] Pending → approved → login transition covered by migration and feature tests.
- [ ] Approval mail delivered on approve.
