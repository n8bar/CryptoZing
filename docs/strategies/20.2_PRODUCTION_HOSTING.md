# MS20 Phase 2 Strategy — Production Hosting

Status: Not Started.
Parent milestone doc: [`docs/milestones/20_MAINNET_CUTOVER_ALPHA_GATE.md`](../milestones/20_MAINNET_CUTOVER_ALPHA_GATE.md)

**Goal:** Stand up the production server that will serve `cryptozing.app`, deploy the app and the article site onto it, and run it privately. The mainnet flip and live payment validation follow in Phases 3 and 4.

## 1. [ ] Host and access

1. [ ] [User] Set the monthly ceiling this has to live under, and record it outside the repo.
2. [ ] [User] Choose the host against that ceiling.
   1. [ ] Find what the ceiling buys at each candidate — the smallest tier that could plausibly carry the stack.
   2. [ ] Price the bill rather than the sticker: backups, snapshots, egress, and managed-service add-ons all draw from the same ceiling.
   3. [ ] Weigh what each host does to the ops load.
      1. [ ] Managed database versus self-run — who owns patching, failover, and backup verification.
      2. [ ] Snapshot and restore tooling, and what a restore costs in downtime.
      3. [ ] Out-of-band console access for when SSH is the thing that broke.
   4. [ ] Confirm the growth path: whether the box resizes in place, and what the next tier up costs.
   5. [ ] Establish the exit path — what it takes to move the box and its data elsewhere — so the pick isn't a one-way door.
   6. [ ] Record the pick and its recurring cost outside the repo.
3. [ ] Fit the stack to the box we bought rather than buying up to the stack.
   1. [ ] Measure the running Sail stack to know what actually has to fit.
   2. [ ] Build off the box — run `composer install` and `npm run build` elsewhere and deploy the artifact, so deploy-time spikes never have to fit in RAM.
   3. [ ] Drop resident services the app can do without: database-backed queue and cache instead of a resident Redis, if that's what separates two tiers.
   4. [ ] Hold PHP-FPM `pm.max_children` to what an invite-only alpha actually serves.
   5. [ ] Tune the database buffer pool to the data we carry, not the default.
   6. [ ] Add a swapfile as the OOM backstop.
4. [ ] Provision the server.
   1. [ ] SSH key auth only; disable password auth and root login.
   2. [ ] Create a non-root deploy user owning the app directory.
   3. [ ] Limit the firewall to SSH, HTTP, and HTTPS.
   4. [ ] Enable unattended security updates.
5. [ ] Point a `cryptozing.app` subdomain at the box for the private window.
6. [ ] Issue TLS on that hostname, then force a renewal to prove the timer works rather than trusting it.

## 2. [ ] Application runtime

1. [ ] Install nginx and PHP-FPM serving `public/`, on the PHP version the app is built against.
2. [ ] Provision the data services.
   1. [ ] Database, with an app database and a least-privilege user.
   2. [ ] Cache, queue, and session backend — Redis or the database, per §1.3.3.
   3. [ ] Credentials generated on the box and written only to the server `.env`.
   4. [ ] Bound to localhost so neither is reachable from the internet.
3. [ ] Put the background processes under supervision.
   1. [ ] Queue worker with restart-on-failure.
   2. [ ] `wallet:watch-payments` alongside it.
   3. [ ] Scheduler as a per-minute system timer.
   4. [ ] All three enabled at boot.
4. [ ] Rotate app and service logs.

## 3. [ ] Deploy path

1. [ ] Build the release artifact off the box per §1.3.2.
   1. [ ] `composer install --no-dev --optimize-autoloader`.
   2. [ ] `npm ci && npm run build`.
2. [ ] Write one repeatable deploy script.
   1. [ ] Ship the artifact into a fresh release directory.
   2. [ ] `migrate --force`.
   3. [ ] Warm the config, route, and view caches.
   4. [ ] Flip `current`, reload PHP-FPM, restart the workers.
3. [ ] Make it run start to finish as the deploy user with no interactive steps.
4. [ ] Keep `.env` on the server only — never in the repo, never in a build artifact.
5. [ ] Keep the watch-only boundary: no seed phrase or private key reaches the box.
6. [ ] Make the previous release restorable without a rebuild.
   1. [ ] Retain the last few releases on disk.
   2. [ ] Roll back by flipping `current` and restarting workers, and prove it once.

## 4. [ ] Article site on the new host

Eleventy keeps feeding Pages until MS21 retires it. Both renderers read the same markdown, so the overlap costs no authoring work.

1. [ ] Port `/learn/*` from Eleventy to Laravel.
   1. [ ] Convert `how-to-invoice-someone-in-bitcoin.njk` to markdown with its HTML inline, so Eleventy and Blade read the same five sources through cutover.
   2. [ ] Port `default.njk` and `article.njk` to Blade layouts.
   3. [ ] Route `/learn` and `/learn/{slug}` to a controller that reads the front matter and renders through those layouts.
   4. [ ] Reproduce the index ordering, including the video card pinned after the article it pairs with.
   5. [ ] Emit the canonical, title, description, and author metadata each article's front matter already carries.
   6. [ ] Match the Pages URLs exactly, trailing slash included — `/learn/what-is-a-bitcoin-invoice/` has to resolve the same or the SEO baseline moves.
   7. [ ] Port the staging mirror onto the same views.
   8. [ ] Serve `sitemap.xml` from the app.
2. [ ] Keep the private hostname out of the index.
   1. [ ] Serve robots by hostname — disallow on the private subdomain, allow on `cryptozing.app` — since one app now answers for both.
   2. [ ] Add `X-Robots-Tag: noindex` on the private hostname from nginx.
   3. [ ] Confirm canonicals still resolve to `cryptozing.app` so this copy never competes with the live site.
3. [ ] Diff the Blade output against the Pages HTML for all five articles and the index, and settle every difference that isn't cosmetic.

## 5. [ ] Backups

1. [ ] Schedule a nightly database dump.
2. [ ] Ship the dumps to storage that isn't the app server.
3. [ ] Set a retention window and prune what ages out.
4. [ ] Restore into a scratch database before Phase 3 touches mainnet.

## 6. [ ] Verification

1. [ ] [Agent] Deploy from a clean checkout.
   1. [ ] Confirm the app boots and migrations run clean.
   2. [ ] Confirm login, register, and dashboard respond over TLS.
   3. [ ] Deploy a second time and confirm the run is idempotent.
2. [ ] [Agent] Test service durability.
   1. [ ] Kill the queue worker and the watcher; confirm supervision restarts both.
   2. [ ] Reboot the box; confirm everything returns without hand-holding.
   3. [ ] Confirm the support dashboard's watcher-stale signal reports correctly from this box — on a tight tier it's the net that catches an OOM-killed watcher.
3. [ ] [Agent] Walk `/learn/*` live on the box.
   1. [ ] Confirm every article URL resolves, trailing slash included, with no redirect hops the Pages build doesn't have.
   2. [ ] Confirm the noindex headers and unchanged canonicals.
4. [ ] [User] Read one ported article end to end against the Pages copy — layout, type, images, links.
5. [ ] [User] Confirm the host account, DNS records, and TLS renewal all sit under accounts you control.

## Exit Criteria

- [ ] Production server provisioned and running the app, private.
- [ ] Article content migrated off GitHub Pages onto the new hosting and serving correctly there.
- [ ] `/learn/*` rendered by Laravel from the same markdown, at URLs identical to the Pages build.
- [ ] Queue worker, scheduler, and watcher supervised and reboot-durable.
- [ ] Deploy repeatable from a clean checkout, with the previous release restorable.
- [ ] TLS issued and renewal proven on the private hostname.
- [ ] Database backup scheduled and a restore proven.
- [ ] Private hostname serves `noindex` with canonicals still pointing at `cryptozing.app`.
