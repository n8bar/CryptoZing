# MS20 Phase 2 Strategy — Production Hosting

Status: Not Started.
Parent milestone doc: [`docs/milestones/20_MAINNET_CUTOVER_ALPHA_GATE.md`](../milestones/20_MAINNET_CUTOVER_ALPHA_GATE.md)

**Goal:** Stand up the production server that will serve `cryptozing.app`, deploy the app and the article site onto it, and run it privately. Production runs the same Docker recipe we publish for self-hosters, which is what backs [`docs/CONTENT_PROMISES.md`](../CONTENT_PROMISES.md) promise 14. The mainnet flip and live payment validation follow in Phases 3 and 4.

## 1. [ ] Host and access

1. [ ] [User] Set the monthly ceiling this has to live under.
2. [ ] [User] Choose the host against that ceiling.
   1. [ ] Find what the ceiling buys at each candidate — the smallest tier that could plausibly carry the stack.
   2. [ ] Price the bill rather than the sticker: backups, snapshots, egress, and managed-service add-ons all draw from the same ceiling.
   3. [ ] Weigh what each host does to the ops load.
      1. [ ] Managed database versus self-run — who owns patching, failover, and backup verification.
      2. [ ] Snapshot and restore tooling, and what a restore costs in downtime.
      3. [ ] Out-of-band console access for when SSH is the thing that broke.
   4. [ ] Confirm the box resizes in place, without a rebuild.
   5. [ ] Price the next tier up, so growth has a known cost rather than a surprise.
   6. [ ] Establish the exit path — what it takes to move the box and its data elsewhere — so the pick isn't a one-way door.
   7. [ ] Record the pick and its recurring cost outside the repo.
3. [ ] Fit the stack to the box we bought rather than buying up to the stack.
   1. [ ] Measure what actually has to fit, from the running Sail stack.
      1. [ ] Peak RSS of a PHP-FPM worker serving a real page.
      2. [ ] Resident footprint of each always-on process — queue worker, watcher, scheduler.
      3. [ ] Database and cache footprint at the data size we expect to carry.
      4. [ ] Disk across app, retained releases, database, staged backups, and logs.
   2. [ ] Decide the cache, queue, and session backend: database-backed instead of a resident Redis, if Redis is what separates two tiers.
   3. [ ] Hold PHP-FPM `pm.max_children` to what an invite-only alpha actually serves.
   4. [ ] Tune the database buffer pool to the data we carry, not the default.
   5. [ ] Add a swapfile as the OOM backstop.
4. [ ] Provision the server.
   1. [ ] SSH key auth only; disable password auth and root login.
   2. [ ] Create a non-root deploy user owning the app directory.
   3. [ ] Limit the firewall to SSH, HTTP, and HTTPS.
   4. [ ] Enable unattended security updates.
5. [ ] Point a `cryptozing.app` subdomain at the box for the private window.
6. [ ] Issue TLS on that hostname.
7. [ ] Force a renewal to prove the timer works — an unproven renewal fails silently, sixty days from now.

## 2. [ ] Application runtime

1. [ ] Install the web tier.
   1. [ ] The PHP version the app is built against, with the extensions composer requires.
   2. [ ] nginx site config with `public/` as the root and the PHP-FPM socket wired.
2. [ ] Provision the data services.
   1. [ ] Install the database engine.
   2. [ ] Create the app database and a user scoped to it and nothing else.
   3. [ ] Stand up the cache, queue, and session backend chosen in §1.3.2.
   4. [ ] Generate credentials on the box and write them only to the server `.env`.
   5. [ ] Bind both to localhost so neither is reachable from the internet.
3. [ ] Put the background processes under supervision.
   1. [ ] Queue worker with restart-on-failure.
   2. [ ] `wallet:watch-payments` alongside it.
   3. [ ] Scheduler as a per-minute system timer.
   4. [ ] All three enabled at boot.
4. [ ] Rotate app and service logs.

## 3. [ ] Deploy path

1. [ ] Build the release artifact off the box, so deploy-time spikes never have to fit in the box's RAM.
   1. [ ] `composer install --no-dev --optimize-autoloader`.
   2. [ ] `npm ci && npm run build`.
2. [ ] Write one repeatable deploy script.
   1. [ ] Ship the artifact into a fresh release directory.
   2. [ ] Symlink the shared `.env` into the release — it lives on the server and never in the artifact.
   3. [ ] `migrate --force`.
   4. [ ] Warm the config, route, and view caches.
   5. [ ] Flip the `current` symlink.
   6. [ ] Reload PHP-FPM so opcache follows the new path.
   7. [ ] Restart the queue worker and watcher so they aren't left running the previous release.
3. [ ] Make it run start to finish as the deploy user with no interactive steps.
4. [ ] Make the previous release restorable without a rebuild.
   1. [ ] Retain the last few releases on disk.
   2. [ ] Write the rollback path: flip `current` back, reload, restart workers.

## 4. [ ] Article site

The site stays static and moves out of the app: its own repo, its own container, its own release cadence. Publishing an article redeploys that container and nothing else. `/learn/*` stays on the apex — MS21 records that those URLs never move.

1. [ ] Split the content site into its own repo.
   1. [ ] Move `site/` and `.github/workflows/pages.yml` across.
   2. [ ] `git rm` both from the app repo, so the app image cannot carry CryptoZing's public content to a self-hosted instance.
   3. [ ] Keep Pages publishing from the new repo until MS21 retires it.
2. [ ] Build the site container.
   1. [ ] Dockerfile running the Eleventy build, with nginx serving the output.
   2. [ ] Publish to the registry on push, same mechanism as the app image.
3. [ ] Serve `/learn/*` from it.
   1. [ ] Proxy `/learn/` from the app's nginx to the site container, TLS terminating once at the front.
   2. [ ] Confirm no collision between article paths and app routes.
4. [ ] Keep the private hostname out of the index.
   1. [ ] Disallow crawling on the private subdomain via robots.
   2. [ ] Add `X-Robots-Tag: noindex` for that hostname at the front nginx, covering both the app and the proxied articles.
   3. [ ] Confirm canonicals still resolve to `cryptozing.app` so this copy never competes with the live site.

## 5. [ ] Backups

1. [ ] Schedule a nightly database dump.
2. [ ] Ship the dumps to storage that isn't the app server.
3. [ ] Set a retention window and prune what ages out.
4. [ ] Restore into a scratch database before Phase 3 touches mainnet.

## 6. [ ] Verification

1. [ ] [Agent] Deploy from a clean checkout.
   1. [ ] Confirm the app boots.
   2. [ ] Confirm migrations run clean.
   3. [ ] Confirm login, register, and dashboard respond over TLS.
   4. [ ] Deploy a second time and confirm the run is idempotent.
   5. [ ] Roll back and confirm the app serves from the previous release.
2. [ ] [Agent] Test service durability.
   1. [ ] Kill the queue worker and the watcher; confirm supervision restarts both.
   2. [ ] Reboot the box; confirm everything returns without hand-holding.
   3. [ ] Confirm the support dashboard's watcher-stale signal reports correctly from this box — on a tight tier it's the net that catches an OOM-killed watcher.
3. [ ] [Agent] Walk `/learn/*` live on the box.
   1. [ ] Confirm every article URL resolves, trailing slash included, with no redirect hops the Pages build doesn't have.
   2. [ ] Confirm the noindex headers and unchanged canonicals.
4. [ ] [Agent] Sweep the box for any seed phrase or private key and confirm there is none — watch-only holds in production or it holds nowhere.
5. [ ] [User] Read one article served from the box against the Pages copy — layout, type, images, links.
6. [ ] [User] Confirm the host account, DNS records, and TLS renewal all sit under accounts you control.

## Exit Criteria

- [ ] Production server provisioned and running the app, private.
- [ ] Article content migrated off GitHub Pages onto the new hosting and serving correctly there.
- [ ] Article site split to its own repo and container, serving `/learn/*` on the apex at URLs identical to the Pages build.
- [ ] App image carries no CryptoZing public content.
- [ ] Queue worker, scheduler, and watcher supervised and reboot-durable.
- [ ] Deploy repeatable from a clean checkout, with the previous release restorable.
- [ ] TLS issued and renewal proven on the private hostname.
- [ ] Database backup scheduled and a restore proven.
- [ ] Private hostname serves `noindex` with canonicals still pointing at `cryptozing.app`.
