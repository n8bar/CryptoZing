# MS20 Phase 2 Strategy — Production Hosting

Status: In Progress.
Parent milestone doc: [`docs/milestones/20_MAINNET_CUTOVER_ALPHA_GATE.md`](../milestones/20_MAINNET_CUTOVER_ALPHA_GATE.md)

**Goal:** Stand up the production server that will serve `cryptozing.app`, deploy the app and the article site onto it, and run it privately. Production runs the same Docker recipe we publish for self-hosters, which is what backs [`docs/CONTENT_PROMISES.md`](../CONTENT_PROMISES.md) promise 14. The mainnet flip and live payment validation follow in Phases 3 and 4.

Section 1 is pure repo and CI work with no dependency on the host, so it can run parallel to the §2 host decision. Everything after that is ordered.

## 1. [x] Article site out of the app repo

The site stays static and moves out: its own repo, its own container, its own release cadence. Publishing an article redeploys that container and nothing else. It goes first because the app image has to be built from a repo that no longer carries CryptoZing's public content.

1. [x] Split the content site into its own repo. [`n8bar/cryptozing-site`](https://github.com/n8bar/cryptozing-site); article history remains in this repo's log.
   1. [x] Move `site/` and `.github/workflows/pages.yml` across. Workflow adapted to root layout.
   2. [x] `git rm` both from the app repo. Living-doc references retargeted (CONTENT_PLAN, BACKLOG, AGENTS).
   3. [x] Keep Pages publishing from the new repo until MS21 retires it. `cryptozing.app` custom domain moved to the new repo's Pages; live URLs verified 200 over TLS.
2. [x] Build the site container.
   1. [x] Dockerfile running the Eleventy build, with nginx serving the output. `CI=true` baked in so Eleventy outputs `_site/`.
   2. [x] Publish to the registry on push, same mechanism the app image will use. `ghcr.io/n8bar/cryptozing-site`, sha + latest tags, workflow green.

## 2. [ ] Host and access

1. [x] [User] Set the monthly ceiling this has to live under.
2. [x] [User] Choose the host against that ceiling. Pick lands the stack on one VPS running the published recipe, with sizable ceiling headroom.
   1. [x] Find what the ceiling buys at each candidate — the smallest tier that could plausibly carry the stack.
   2. [x] Price the bill rather than the sticker: backups, snapshots, egress, and managed-service add-ons all draw from the same ceiling.
   3. [x] Weigh what each host does to the ops load.
      1. [x] Managed database versus self-run — who owns patching, failover, and backup verification. Self-run in Compose, deliberately — the published recipe runs MySQL in Compose, so a managed DB would deviate from promise 14.
      2. [x] Snapshot and restore tooling, and what a restore costs in downtime.
      3. [x] Out-of-band console access for when SSH is the thing that broke.
   4. [x] Confirm the box resizes in place, without a rebuild. Pick trades this away for cost — growth path is a migrate via the §2.2.6 exit, acceptable because the recipe makes that cheap.
   5. [x] Price the next tier up, so growth has a known cost rather than a surprise. Next tier fits inside the ceiling.
   6. [x] Establish the exit path — what it takes to move the box and its data elsewhere — so the pick isn't a one-way door. The recipe is portable by design; exit = restore the §5 dump behind `compose up` elsewhere.
   7. [x] Record the pick and its recurring cost outside the repo. BUSINESS_OPS_NOTES.md.
3. [ ] Fit the stack to the box we bought rather than buying up to the stack.
   1. [ ] Measure what actually has to fit, from the running Sail stack.
      1. [ ] Peak RSS of a PHP-FPM worker serving a real page.
      2. [ ] Resident footprint of each always-on process — queue worker, watcher, scheduler.
      3. [ ] Database and cache footprint at the data size we expect to carry.
      4. [ ] Docker daemon and per-container overhead on top of all of it.
      5. [ ] Disk across images, volumes, database, staged backups, and logs.
   2. [ ] Decide the cache, queue, and session backend: database-backed instead of a Redis container, if Redis is what separates two tiers.
   3. [ ] Hold PHP-FPM `pm.max_children` to what an invite-only alpha actually serves.
   4. [ ] Tune the database buffer pool to the data we carry, not the default.
   5. [ ] Add a swapfile as the OOM backstop.
4. [x] Provision the server. AlmaLinux updated 9.0→9.8; NIC migrated from legacy network-scripts to NetworkManager; reboot-verified on the new kernel.
   1. [x] Create a non-root deploy user. `deploy`, key auth verified.
   2. [x] Install Docker Engine and the compose plugin. docker-ce 29.7.2, Compose v5.4.0, enabled at boot.
   3. [x] Grant the deploy user docker access. `docker ps` verified as deploy.
   4. [x] Limit the firewall to SSH, HTTP, and HTTPS. firewalld; cockpit/dhcpv6-client removed.
   5. [x] Enable unattended security updates. dnf-automatic, security-only, apply_updates, timer active.
5. [x] Point a `cryptozing.app` subdomain at the box for the private window. `alpha.cryptozing.app`, A-only, verified resolving.
6. [x] Issue TLS for that hostname on the host, into a directory the nginx container mounts read-only. certbot standalone → `/etc/letsencrypt`; §3 nginx mounts it ro.
7. [x] Force a renewal to prove the timer works — an unproven renewal fails silently, sixty days from now. `certbot-renew.timer` active; forced renewal rotated the serial.
8. [x] Reload the nginx container on renewal, so a fresh cert is served rather than sitting unused on disk. Deploy hook installed, no-ops until the container exists; live proof is §6.1.6.

## 3. [ ] Production image and compose

This is the recipe published for self-hosters, and the one our own box runs.

1. [ ] Write the production Dockerfile, separate from Sail's dev images under `docker/`.
   1. [ ] PHP-FPM on the version the app targets, with the extensions composer requires.
   2. [ ] Application code and built assets baked in, so nothing installs at runtime.
   3. [ ] Runs as a non-root user.
   4. [ ] No dev dependencies, no Sail tooling, no `.env`.
2. [ ] Write the production compose file, separate from `compose.yaml`.
   1. [ ] App service.
      1. [ ] Runs the app image.
      2. [ ] Bind mount for `storage/`, so uploads and logs survive a container replacement.
      3. [ ] Healthcheck.
   2. [ ] nginx service.
      1. [ ] Publishes 80 and 443.
      2. [ ] Mounts the host cert directory read-only.
   3. [ ] Database service.
      1. [ ] Internal network only, no published port.
      2. [ ] Named volume for its data.
      3. [ ] Healthcheck.
	  4. [ ] Take a few moments and lets ensure that we have first class data privacy and security working for us in behalf of our users' data.
   4. [ ] Queue worker service off the app image.
   5. [ ] Watcher service off the app image.
   6. [ ] Scheduler service off the app image.
   7. [ ] `restart: unless-stopped` across every service — this is what replaces host supervision.
   8. [ ] `env_file` on every service, pointing at a host `.env` that never enters the image.
   9. [ ] Log driver size and rotation caps across every service, so container logs can't fill the disk.
3. [ ] Wire the article site in at our deployment only, since the published recipe ships without it.
   1. [ ] Proxy `/learn/` from the front nginx to the §1.2 site container, TLS terminating once at the front.
   2. [ ] Confirm no collision between article paths and app routes.
4. [ ] Keep the private hostname out of the index.
   1. [ ] Disallow crawling on the private subdomain via robots.
   2. [ ] Add `X-Robots-Tag: noindex` for that hostname at the front nginx, covering both the app and the proxied articles.
   3. [ ] Confirm canonicals still resolve to `cryptozing.app` so this copy never competes with the live site.
5. [ ] Ship `.env.example` with defaults safe for someone who isn't us.
   1. [ ] `DONATION_WALLET_XPUB` blank, so `/donate` is absent ([#135](https://github.com/n8bar/CryptoZing/issues/135)).
   2. [ ] `MAIL_ALIAS_ENABLED=false`, so their mail is never rewritten to our catch-all.
   3. [ ] `APP_KEY` generated per install rather than shipped.
6. [ ] Write the production self-host guide under `docs/ops/get-live/` — this is what backs promise 14.

## 4. [ ] Deploy path

1. [ ] Build and publish images in CI, never on the box.
   1. [ ] Build the app image on push to `main`.
   2. [ ] Tag by commit sha.
   3. [ ] Push to GHCR, free for a public repo.
2. [ ] Write the deploy.
   1. [ ] Pull the tag onto the box.
   2. [ ] Run migrations in a one-shot container before services switch.
   3. [ ] `compose up -d` to roll services onto the new tag.
   4. [ ] Confirm no containers are left orphaned on the old tag.
3. [ ] Make it run start to finish as the deploy user with no interactive steps.
4. [ ] Keep the last few tags pullable, so rollback is re-deploying the previous one.

## 5. [ ] Backups

1. [ ] Schedule a nightly database dump.
2. [ ] Ship the dumps to storage that isn't the app server.
	1. [ ] Implement or defer first class security and encryption on the backups.
3. [ ] Set a retention window and prune what ages out.
4. [ ] Restore into a scratch database before Phase 3 touches mainnet.

## 6. [ ] Verification

1. [ ] [Agent] Deploy a published image tag.
   1. [ ] Confirm the app boots.
   2. [ ] Confirm migrations run clean.
   3. [ ] Confirm login, register, and dashboard respond over TLS.
   4. [ ] Deploy the same tag again and confirm the run is idempotent.
   5. [ ] Roll back to the previous tag and confirm the app serves from it.
   6. [ ] Force a cert renewal with the stack up and confirm the front nginx serves the new serial (§2.8 hook's live proof).
2. [ ] [Agent] Stand up the published recipe from scratch as a self-hoster would, on a blank `.env`.
   1. [ ] Confirm it runs without any CryptoZing-specific value.
   2. [ ] Confirm `/donate` is absent and the Support CryptoZing link is what shows.
   3. [ ] Confirm no article content is served.
3. [ ] [Agent] Test service durability.
   1. [ ] Kill the queue worker and the watcher; confirm the restart policy brings both back.
   2. [ ] Reboot the box; confirm everything returns without hand-holding.
   3. [ ] Confirm the support dashboard's watcher-stale signal reports correctly from this box — on a tight tier it's the net that catches an OOM-killed watcher.
4. [ ] [Agent] Walk `/learn/*` live on the box.
   1. [ ] Confirm every article URL resolves, trailing slash included, with no redirect hops the Pages build doesn't have.
   2. [ ] Confirm the noindex headers and unchanged canonicals.
5. [ ] [Agent] Sweep the box and the published image for any seed phrase or private key — watch-only holds in production or it holds nowhere.
6. [ ] [User] Read one article served from the box against the Pages copy — layout, type, images, links.
7. [ ] [User] Confirm the host account, DNS records, and TLS renewal all sit under accounts you control.

## Exit Criteria

- [ ] Article site split to its own repo and container, serving `/learn/*` on the apex at URLs identical to the Pages build.
- [ ] App image carries no CryptoZing public content.
- [ ] Production server provisioned and running the app, private.
- [ ] Production runs the same Docker recipe published for self-hosters, backing promise 14.
- [ ] A self-host instance stood up from that recipe serves no CryptoZing content and no `/donate`.
- [ ] Article content migrated off GitHub Pages onto the new hosting and serving correctly there.
- [ ] Queue worker, scheduler, and watcher supervised and reboot-durable.
- [ ] Deploy repeatable from a clean checkout, with the previous release restorable.
- [ ] TLS issued and renewal proven on the private hostname.
- [ ] Database backup scheduled and a restore proven.
- [ ] Private hostname serves `noindex` with canonicals still pointing at `cryptozing.app`.
