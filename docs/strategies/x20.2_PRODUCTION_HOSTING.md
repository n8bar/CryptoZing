# MS20 Phase 2 Strategy — Production Hosting

Status: Complete.
Parent milestone doc: [`docs/milestones/x20_MAINNET_CUTOVER_ALPHA_GATE.md`](../milestones/x20_MAINNET_CUTOVER_ALPHA_GATE.md)

**Goal:** Stand up the production server that will serve `cryptozing.app`, deploy the app and the article site onto it, and run it privately. Production runs the same Docker recipe we publish for self-hosters, which is what backs [`docs/CONTENT_PROMISES.md`](../CONTENT_PROMISES.md) promise 14. The mainnet flip and live payment validation follow in Phases 3 and 4.

Section 1 is pure repo and CI work with no dependency on the host, so it can run parallel to the §2 host decision. Everything after that is ordered.

## 1. [x] Article site out of the app repo

The site stays static and moves out: its own repo, its own container, its own release cadence. Publishing an article redeploys that container and nothing else. It goes first because the app image has to be built from a repo that no longer carries CryptoZing's public content.

1. [x] Split the content site into its own repo. [`n8bar/cryptozing-site`](https://github.com/n8bar/cryptozing-site); article history remains in this repo's log.
   1. [x] Move `site/` and `.github/workflows/pages.yml` across. Workflow adapted to root layout.
   2. [x] `git rm` both from the app repo. Living-doc references retargeted (CONTENT_PLAN, BACKLOG, AGENTS).
   3. [x] Keep Pages publishing from the new repo until MS21 retires it. `cryptozing.app` custom domain moved to the new repo's Pages; live URLs verified 200 over TLS.
2. [x] Build the site container.
   1. [x] Dockerfile running the Eleventy build, with nginx serving the output. `CI=true` baked in so Eleventy outputs `_site/`.
   2. [x] Publish to the registry on push, same mechanism the app image will use. `ghcr.io/n8bar/cryptozing-site`, sha + latest tags, workflow green.

## 2. [x] Host and access

1. [x] [User] Set the monthly ceiling this has to live under.
2. [x] [User] Choose the host against that ceiling. Pick lands the stack on one VPS running the published recipe, with sizable ceiling headroom.
   1. [x] Find what the ceiling buys at each candidate — the smallest tier that could plausibly carry the stack.
   2. [x] Price the bill rather than the sticker: backups, snapshots, egress, and managed-service add-ons all draw from the same ceiling.
   3. [x] Weigh what each host does to the ops load.
      1. [x] Managed database versus self-run — who owns patching, failover, and backup verification. Self-run in Compose, deliberately — the published recipe runs MySQL in Compose, so a managed DB would deviate from promise 14.
      2. [x] Snapshot and restore tooling, and what a restore costs in downtime.
      3. [x] Out-of-band console access for when SSH is the thing that broke.
   4. [x] Confirm the box resizes in place, without a rebuild. Pick trades this away for cost — growth path is a migrate via the §2.2.6 exit, acceptable because the recipe makes that cheap.
   5. [x] Price the next tier up, so growth has a known cost rather than a surprise. Next tier fits inside the ceiling.
   6. [x] Establish the exit path — what it takes to move the box and its data elsewhere — so the pick isn't a one-way door. The recipe is portable by design; exit = restore the §6 dump behind `compose up` elsewhere.
   7. [x] Record the pick and its recurring cost outside the repo. BUSINESS_OPS_NOTES.md.
3. [x] Fit the stack to the box we bought rather than buying up to the stack. Fixed costs ≈1.5 GB against 3.6 GB; >1 GB headroom at the worker cap below.
   1. [x] Measure what actually has to fit, from the running Sail stack.
      1. [x] Peak RSS of a PHP-FPM worker serving a real page. ~86 MB warm (dev cli-server as FPM proxy).
      2. [x] Resident footprint of each always-on process — queue worker, watcher, scheduler. ~82 MB each; watcher is a per-minute scheduled run (~80 MB transient), not always-on.
      3. [x] Database and cache footprint at the data size we expect to carry. MySQL ~515 MB resident at defaults; app schema 49 MB on disk; cache is in-database.
      4. [x] Docker daemon and per-container overhead on top of all of it. dockerd+containerd 136 MB measured on the box; ~10 MB/container shims.
      5. [x] Disk across images, volumes, database, staged backups, and logs. DB volume <1 GB including redo; 53 GB free on the box — no pressure.
   2. [x] Decide the cache, queue, and session backend: database-backed instead of a Redis container, if Redis is what separates two tiers. All three database-backed; queue+cache already are, sessions flip file→database (table ships in the base migration).
   3. [x] Hold PHP-FPM `pm.max_children` to what an invite-only alpha actually serves. Cap = 8 (~720 MB worst case); config lands in §3.1.
   4. [x] Tune the database buffer pool to the data we carry, not the default. `innodb_buffer_pool_size=256M`; config lands in §3.2.3.
   5. [x] Add a swapfile as the OOM backstop. Box ships a 2 G swap partition (`/dev/vda2`) — already covered.
4. [x] Provision the server. AlmaLinux updated 9.0→9.8; NIC migrated from legacy network-scripts to NetworkManager; reboot-verified on the new kernel.
   1. [x] Create a non-root deploy user. `deploy`, key auth verified.
   2. [x] Install Docker Engine and the compose plugin. docker-ce 29.7.2, Compose v5.4.0, enabled at boot.
   3. [x] Grant the deploy user docker access. `docker ps` verified as deploy.
   4. [x] Limit the firewall to SSH, HTTP, and HTTPS. firewalld; cockpit/dhcpv6-client removed.
   5. [x] Enable unattended security updates. dnf-automatic, security-only, apply_updates, timer active.
   6. [x] Rate-limit SSH brute force with fail2ban. sshd jail, systemd backend, firewalld actions; banned 2 IPs on first start from pre-existing journal noise.
5. [x] Point a `cryptozing.app` subdomain at the box for the private window. `alpha.cryptozing.app`, A-only, verified resolving.
6. [x] Issue TLS for that hostname on the host, into a directory the nginx container mounts read-only. certbot standalone → `/etc/letsencrypt`; §3 nginx mounts it ro.
7. [x] Force a renewal to prove the timer works — an unproven renewal fails silently, sixty days from now. `certbot-renew.timer` active; forced renewal rotated the serial.
8. [x] Reload the nginx container on renewal, so a fresh cert is served rather than sitting unused on disk. Deploy hook installed, no-ops until the container exists; live proof is §5.1.6.
9. [x] Switch the renewal authenticator from standalone to webroot when the stack first binds port 80 — standalone renewals fail silently once nginx owns the port. `authenticator = webroot` persisted in the renewal conf; proven live at §5.1.6.

## 3. [x] Production image and compose

This is the recipe published for self-hosters, and the one our own box runs.

1. [x] Write the production Dockerfile, separate from Sail's dev images under `docker/`. `docker/production/Dockerfile`, 219 MB, boot + derivation + extensions smoke-tested.
   1. [x] PHP-FPM on the version the app targets, with the extensions composer requires. 8.4-fpm-alpine + pdo_mysql/bcmath/intl/opcache/pcntl; Node 20 + runtime node_modules for `derive-address.cjs`.
   2. [x] Application code and built assets baked in, so nothing installs at runtime. Multi-stage: composer no-dev, Vite build, `npm ci --omit=dev`.
   3. [x] Runs as a non-root user. uid 1000, matching the deploy user for the storage bind mount.
   4. [x] No dev dependencies, no Sail tooling, no `.env`. `.dockerignore` also drops the dev package-discovery cache, which otherwise breaks a no-dev boot.
2. [x] Write the production compose file, separate from `compose.yaml`. `compose.production.yaml`.
   1. [x] App service.
      1. [x] Runs the app image. `ghcr.io/n8bar/cryptozing-app:${CZ_TAG}`.
      2. [x] Bind mount for `storage/`, so uploads and logs survive a container replacement.
      3. [x] Healthcheck. FPM ping via fcgi.
   2. [x] nginx service.
      1. [x] Publishes 80 and 443. envsubst template keyed on `CZ_SERVER_NAME`; ACME webroot for renewals while nginx holds 80.
      2. [x] Mounts the host cert directory read-only.
   3. [x] Database service.
      1. [x] Internal network only, no published port.
      2. [x] Named volume for its data.
      3. [x] Healthcheck. mysqladmin ping.
	  4. [x] Take a few moments and lets ensure that we have first class data privacy and security working for us in behalf of our users' data. Verified in place: encrypted casts on xpubs + TOTP secrets, bcrypt passwords, scoped DB user, internal-only DB network, secret-free web container; app-layer encryption is the control at this tier — no disk-level encryption.
	     1. [x] `chmod 600` the host `.env` (deploy-owned) as part of first deploy.
	     2. [x] [User] Store `APP_KEY` in the password manager off-box the moment it's generated at first deploy — backups are unreadable without it.
	     3. [x] Backup-dump encryption is actioned at §6.2.1 — the open work item lives there.
   4. [x] Queue worker service off the app image.
   5. [x] Watcher service off the app image. Covered by the scheduler — the watcher is a per-minute scheduled run (§2.3.1.2), not a separate always-on service.
   6. [x] Scheduler service off the app image.
   7. [x] `restart: unless-stopped` across every service — this is what replaces host supervision.
   8. [x] `env_file` on every service, pointing at a host `.env` that never enters the image. Exception by design: web gets only `CZ_SERVER_NAME`, no app secrets.
   9. [x] Log driver size and rotation caps across every service, so container logs can't fill the disk. json-file 10m×3.
3. [x] Wire the article site in at our deployment only, since the published recipe ships without it. `compose.alpha.yaml` overlay + alpha nginx template.
   1. [x] Proxy `/learn/` from the front nginx to the §1.2 site container, TLS terminating once at the front. Live walk rides §5.4.
   2. [x] Confirm no collision between article paths and app routes. No `/learn` app route; article root-relative assets (favicons, `/images/CZ.png`) all resolve app-side.
4. [x] Keep the private hostname out of the index. In the alpha nginx template; live confirmation rides §5.4.2.
   1. [x] Disallow crawling on the private subdomain via robots. Deny-all `robots.txt` served at the front.
   2. [x] Add `X-Robots-Tag: noindex` for that hostname at the front nginx, covering both the app and the proxied articles.
   3. [x] Confirm canonicals still resolve to `cryptozing.app` so this copy never competes with the live site. Articles carry them in-page; app pages ship none, covered by the header.
5. [x] Ship `.env.example` with defaults safe for someone who isn't us. Also: `APP_URL=localhost`, example.com from-address, `SESSION_DRIVER=database` (§2.3.2), and `ALPHA_GATE_ENABLED=false` so a fresh self-host doesn't lock its own registrations behind our gate.

4. [x] Keep the last few tags pullable, so rollback is re-deploying the previous one. GHCR retains every sha tag; on-box prune is dangling-only; rollback proof is §5.1.5.
