# MS20 Phase 4 Strategy — Mainnet Environment & Wallets

Status: In Progress.
Parent milestone doc: [`docs/milestones/20_MAINNET_CUTOVER_ALPHA_GATE.md`](../milestones/20_MAINNET_CUTOVER_ALPHA_GATE.md)

**Goal:** Bring the deployed box onto a clean mainnet baseline and configure it for the private window, with two separate watch-only xpubs onboarded and their derived addresses verified against the source wallets before any funds move. Phase 5 sends the first real payment.

## 1. [x] Operator wallets

Section 1 gates the rest of the phase and only the operator can do it.

1. [x] [User] Create the mainnet invoice wallet and export its Taproot (BIP86) account key — Phase 3 must land first so onboarding accepts it.
2. [x] [User] Create a separate mainnet donation wallet and export its Taproot account key.
3. [x] [User] Confirm the two xpubs are different keys, not two accounts under one — a shared key collides derivation chains and destroys attribution, which is the MS14 failure. Confirmed: separate, distinct BIP39 seeds.
4. [x] [User] Keep both seeds off the box, out of the repo, and out of any password field in the app. Confirmed: offline primary backup; operator-side encrypted cloud copy only.

## 2. [x] Clean mainnet baseline

Flipping the network on top of testnet rows strands them: addresses derived on one network never match the other, and the watcher would be reconciling against a chain those rows were never on. The app holds only seed and test data, so the baseline starts empty.

1. [x] Drop the testnet database and bring up an empty one.
2. [x] Run migrations against it with no seeders.
3. [x] Confirm nothing survived: no wallet accounts, key cursors, invoices, payments, or donation rows. Zero rows across users, wallet_settings, user_wallet_accounts, wallet_key_cursors, invoices, invoice_payments, donations, clients.
4. [x] Create the operator account fresh, and approve it through the Phase 1 gate. `cz.support@cryptozing.app` (user 1), bootstrapped via tinker — no approved approver exists on a fresh DB; doubles as the support agent account, `SUPPORT_AGENT_EMAILS` updated to match.

## 3. [ ] Mainnet environment

1. [x] Set `WALLET_NETWORK=mainnet`.
   1. [ ] Confirm the watcher picks up `MEMPOOL_MAINNET_URL` from that alone — the network selects the mempool base, so there is no second provider knob to flip. Proof rides §6.3.
2. [x] Replace the single confirmation threshold with value-tiered confirmations per [`docs/specs/PARTIAL_PAYMENTS+CONFIRMATIONS.md`](../specs/PARTIAL_PAYMENTS+CONFIRMATIONS.md) §Confirmation Gate — built now so no existing user ever gets the behavior change dumped on them.
   1. [x] Implement: required count resolves from the invoice's USD value at creation; donations use the fewest-confirmations tier; boundaries and counts operator-configurable. `ConfirmationPolicy`, `BLOCKCHAIN_CONFIRMATION_TIERS`.
   2. [x] Configure the production ladder: under $500 → 1 conf; $500–$5,000 → 2; $5,000–$50,000 → 3; $50,000+ → 6. Set on the box; live once the Phase-4 image deploys.
   3. [x] Merge this branch's PR and deploy the resulting image tag, so §4/§6 verify against tiered-confirmation code. PR [#144](https://github.com/n8bar/CryptoZing/pull/144) → tag `490f455`; live policy on the box resolves $10k → 3 confs.
3. [x] Point `APP_PUBLIC_URL` at the private hostname, so invoice links and mail resolve to the box rather than localhost or the apex. Already `${APP_URL}` → `https://alpha.cryptozing.app`.
4. [x] Set `MAIL_ALIAS_ENABLED=false` for the private window — Phase 5 has to prove receipts land in a real inbox, which aliasing to the catch-all would hide. Was already false; verified.
5. [x] Set `DONATION_WALLET_XPUB` to the §1.2 key, which is also what makes `/donate` exist on our deployment ([#135](https://github.com/n8bar/CryptoZing/issues/135)).
6. [x] Set `DONATION_NOTIFY_EMAIL` to a mailbox you actually read. `donation.cz@cryptozing.app`.
7. [x] Restart the app, worker, watcher, and scheduler services so every one of them holds the new environment. Recreated app/queue/scheduler; running app reports mainnet + production.

## 4. [ ] Onboard and verify the keys

Nothing in this section moves money. It runs before Phase 5 precisely so a derivation mismatch is found while an error costs nothing.

1. [x] Onboard the invoice xpub at `/wallet/settings`.
2. [x] Derive the first several invoice addresses in the app. Indexes 0–4, static derivation, cursors untouched.
3. [ ] [User] Compare them against the same derivation path in the source wallet, and stop the phase on any mismatch.
   1. [ ] [User] In the invoice wallet app, list the first five receive addresses (path `m/86'/0'/0'/0/0`–`0/4`).
   2. [ ] [User] Compare index-by-index against the §4.2 list.
   3. [ ] [User] Report the verdict; any mismatch stops the phase.
4. [x] Confirm the app does not flag the key as an unsupported wallet configuration. mainnet/bip86, `unsupported_configuration_active=false`.
5. [ ] Derive a donation address and compare it against the donation wallet the same way.
6. [ ] Confirm the invoice and donation chains advance independently — one key's cursor must not move when the other allocates.

## 5. [ ] Watch-only audit

1. [ ] Search the box, the published image, and the repo for anything seed-shaped or key-shaped.
2. [ ] Confirm the database holds public keys only.
3. [ ] Confirm no app flow asks for or accepts a private key.

## 6. [ ] Verification

1. [ ] [Agent] Confirm the running services report mainnet, not testnet.
2. [ ] [Agent] Create a draft invoice and confirm its address is a mainnet address on the operator key's chain.
3. [ ] [Agent] Run the watcher against that address and confirm it queries the mainnet mempool endpoint and returns clean.
4. [ ] [Agent] Load `/donate` and confirm it allocates from the donation key, not the invoice key.
5. [ ] [User] Confirm both derived addresses appear in your source wallets as expected receive addresses.

## Exit Criteria

- [ ] App on a clean mainnet baseline, with no testnet-derived rows carried over.
- [ ] `WALLET_NETWORK=mainnet`, with the watcher on the mainnet mempool endpoint.
- [ ] `APP_PUBLIC_URL` and mail configured for the private window, aliasing off.
- [ ] Operator invoice xpub and mainnet donation xpub onboarded as separate watch-only keys.
- [ ] `/donate` present on our deployment because its xpub is set.
- [ ] Derived invoice and donation addresses verified against the source wallets before any funds move.
- [ ] Watch-only verified — no seed or private keys in repo, image, config, database, or app flows.
