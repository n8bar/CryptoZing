# M21 Phase 1 Strategy — Pre-deploy Verification

Status: Draft for review — execution not started.
Drafted: 2026-09-05.
Parent milestone: [`21_OB_DEPLOYMENT.md`](../milestones/21_OB_DEPLOYMENT.md)
Next phase: [`21.2_DEPLOY_AND_CUTOVER.md`](21.2_DEPLOY_AND_CUTOVER.md)

Goal: leave a verified release and cutover plan for opening the existing mainnet deployment under the apex hostname.

Scope comes from the parent milestone, [`PRODUCT_SPEC.md`](../PRODUCT_SPEC.md), and the linked domain specs. M20's completed [hosting](x20.2_PRODUCTION_HOSTING.md), [wallet](x20.4_MAINNET_ENVIRONMENT_WALLETS.md), and [live-validation](x20.5_LIVE_MAINNET_VALIDATION_BACKOUT.md) strategies provide the starting evidence. Existing mainnet records and wallet lineage survive this cutover.

## Execution and ownership

Run sections in order except the parallel work identified below. `Agent` owns terminal/repo work; `Guided User` owns account-tool actions requiring coaching; `User` owns wallet actions, eyes-on judgments, and acceptance.

Check conditional work only when performed. When a branch does not apply, record that disposition on the item; check off the assessment after its outcome and follow-up owner are recorded.

Drive our VPS through one-shot `ssh deploy@<box> '<command>'` invocations in `/opt/cryptozing`. Every production Compose invocation includes `-f compose.production.yaml -f compose.alpha.yaml`; that overlay supplies the content container and front nginx configuration. Review its effective configuration for apex use in §4. The watcher runs inside the scheduler. Local artisan/composer/npm commands go through Sail.

Keep private configuration, addresses, backup paths, and recovery artifacts in local-only storage under `.cybercreek/` per its local rules. Tracked checkoffs carry IDs, artifact tags, and verdicts.

Safe parallel work after §1: delegate the content repo's nav/URL checks (§4) separately from app/nginx changes; delegate the isolated self-host verification (§8) once the release candidate exists. Analytics (§6) can be prepared alongside routing, with one agent owning shared VPS/Compose edits. Legal copy ownership stays separate from the analytics implementation and integrates after its disposition.

## 2. [ ] Verify recovery readiness

1. [ ] [Agent] Record the deployed `CZ_TAG`, content image tag, and current host/Compose configuration as the rollback baseline.
2. [ ] [Agent] Confirm the prior images are available on the VPS and assess migration compatibility with the proposed release.
3. [ ] [Agent] Take a fresh encrypted database backup using the established backup path.
   1. [ ] Confirm the off-box `age` identity and separately retained `APP_KEY` are available without exposing them in tracked output.
   2. [ ] Restore the dump into an isolated scratch database and verify its schema, row counts, and a known record.
   3. [ ] Confirm `cache`, `cache_locks`, and `sessions` are present with schema only.
4. [ ] [Agent] Check the latest off-box backup pull and retention result.
5. [ ] [Agent] Review the [halt procedure](../ops/RUNNING_THE_SERVER.md#halt-procedure) against this release and add hostname, DNS, content-image, and webhook recovery steps to the local cutover record. A DNS reversal cannot recall cached answers or mail already delivered.

## 3. [ ] Revalidate the existing wallets

1. [ ] [Agent] Run `wallet:check-config` on the production release candidate; stop this phase on a failure.
2. [ ] [Agent] Verify the configured invoice and donation keys still resolve to distinct mainnet accounts with the expected script types.
3. [ ] [Agent] Derive a fresh index-by-index sample from each configured key without advancing production allocation state.
   1. [ ] [User] Compare the invoice sample with the source invoice wallet.
   2. [ ] [User] Compare the donation sample with the source donation wallet.
   3. [ ] [Agent] Record the comparison verdict; any mismatch blocks Phase 2 and mail/payment exercises.
4. [ ] [Agent] Check for unsupported wallet configuration and resolve any unexpected flag before cutover.
5. [ ] [Agent] Verify independent invoice/donation allocation using an isolated copy or a transaction that rolls back; confirm production cursors are unchanged afterward.
6. [ ] [Agent] Read back the production confirmation tiers and `DONATION_NOTIFY_EMAIL` / `DONATION_MAX_UNPAID_ADDRESSES`; confirm they match the intended mainnet configuration and [`DONATIONS.md`](../specs/DONATIONS.md).

## 4. [ ] Prepare apex routing and preserve discovery

1. [ ] [Agent] Capture the currently served apex URL baseline: `/`, published `/learn/*`, required assets, `/robots.txt`, `/sitemap.xml`, `/terms`, and `/privacy`.
   1. [ ] Record status/redirect targets for HTTP, HTTPS, and `www` variants.
   2. [ ] Record canonical, social, structured-data, and indexing signals for the landing page and representative articles.
   3. [ ] [Guided User] Capture Search Console and Bing property/sitemap status using the existing M15 verifications.
2. [ ] [Agent] Prepare the deployment-specific nginx/Compose changes needed to serve the apex landing page and proxy content to the separate site container.
   1. [ ] Make published apex pages crawlable while retaining noindex for alpha/staging and public invoice surfaces.
   2. [ ] Preserve the baseline `/learn/*` paths, assets, slash redirects, and the established HTTPS/non-`www` canonical behavior.
   3. [ ] Verify the apex sitemap includes the published content and uses the correct host; confirm robots permits public-site crawling.
3. [ ] [Agent] Exercise existing alpha-issued public and signed mail links against the proposed host configuration; prepare continued alpha-host handling for links that would fail after a redirect, including signature validation.
4. [ ] [Agent] Update the content repo's main nav to remove the pre-release GitHub link, retaining the footer link; verify its app/content navigation against the cutover routing.
5. [ ] [Agent] Inspect apex/`www` DNS records and TTLs; record the cutover and recovery values while preserving mail and webmaster-verification records.
6. [ ] [Agent] Prepare the certificate issuance and renewal sequence for apex and redirect hosts. Verify a challenge path that can issue the certificate while normal apex traffic still goes to Pages, and account for nginx already owning port 80.
7. [ ] [Agent] Verify the prepared routing with host-aware requests in the rehearsal environment; record the app and site image tags that passed.

4. [ ] [Agent] Verify staging/noindex pages, signed-in app pages, and invoice pages send no analytics, and that no duplicate Cloud event is sent.

## 8. [ ] Verify the release and self-host boundary

1. [ ] [Agent] Land required app/config fixes through their source-branch PRs with specs updated first for any behavior change; require green `PR Tests` and run the local Sail suite for code changes.
2. [ ] [Agent] Verify the intended production app image using the [published self-host guide](../ops/get-live/README.md) on an isolated blank environment with its own secrets/storage.
   1. [ ] Confirm the base Compose recipe starts without our alpha overlay or production environment.
   2. [ ] Complete account/wallet onboarding with test-owned public derivation material and create an invoice.
   3. [ ] Confirm the app image carries no CryptoZing article site and a blank donation key leaves the configured-donation page absent, per the donation spec.

4. [ ] [Agent] Record a Phase 2 handoff containing verified artifact tags, planned environment/DNS/webhook changes, recovery references, analytics disposition, and outstanding user-owned cutover actions.

## Exit Criteria

- [ ] Recovery readiness is verified against the release, including a fresh scratch restore and access to off-box secrets.
- [ ] Wallet and mail preflight passed; production data and allocation state are preserved.
- [ ] Apex routing, indexing, existing-link handling, and TLS/DNS sequence are prepared and verified.
- [ ] Analytics has a completed or explicitly deferred disposition, with matching legal publication copy reviewed.
- [ ] The release passes applicable local/CI checks and the clean self-host verification.
- [ ] Every readiness finding is resolved or assigned to a named later acceptance check; no unresolved prerequisite is handed to Phase 2 as passed.
