# M21 Phase 1 Strategy — Pre-deploy Verification

Status: Draft for review — execution not started.
Parent milestone: [`21_OB_DEPLOYMENT.md`](../milestones/21_OB_DEPLOYMENT.md)
Next: [M21.2 — Deploy and cutover](21.2_DEPLOY_AND_CUTOVER.md)

Goal: prepare the existing mainnet deployment for the apex release. [Shared references](../milestones/21_OB_DEPLOYMENT.md#execution-references) govern workflow and operations.

Parallel work: content-repo navigation (§4) and analytics (§6) can proceed alongside app routing; keep shared VPS/Compose edits with one owner. Delegate self-host verification (§8) once the candidate exists. Legal preparation (§7) follows the analytics disposition.

## 1. [ ] Establish the release baseline

1. [ ] [User] Approve the three M21 phase strategies.
2. [ ] Compare deployed app/site tags with their canonical `main` branches; identify release candidates and required fixes.
3. [ ] Confirm the private production/mainnet deployment retains its expected invoice/donation data and enabled alpha gate.

## 2. [ ] Verify recovery readiness

1. [ ] Record rollback app/site tags and host/Compose configuration.
2. [ ] Verify cached rollback images and migration compatibility.
3. [ ] Take a fresh encrypted backup per the [backup runbook](../ops/RUNNING_THE_SERVER.md#backups).
   1. [ ] Verify access to the off-box decrypting identity and retained `APP_KEY`.
   2. [ ] Validate a scratch restore per the runbook, including its schema-only exclusions.
4. [ ] Check the latest off-box pull and retention result.
5. [ ] Add DNS, hostname, site-image, and webhook reversal steps to the cutover record alongside the existing halt procedure.

## 3. [ ] Check wallets against the alpha baseline

1. [ ] Run `wallet:check-config` against the candidate; resolve failures and unexpected unsupported-wallet flags before cutover.
2. [ ] Compare wallet derivation/allocation code, keys/script types, network, confirmation tiers, and [donation settings](../specs/DONATIONS.md) with the verified [M20.4](x20.4_MAINNET_ENVIRONMENT_WALLETS.md) / [M20.5](x20.5_LIVE_MAINNET_VALIDATION_BACKOUT.md) alpha baseline.
3. [ ] Record which address/allocation checks need repeating because of relevant changes, failed checks, or an uncertain baseline; otherwise retain alpha's proof.
   1. [ ] For required address proof, derive fresh samples using the [M20.4 comparison procedure](x20.4_MAINNET_ENVIRONMENT_WALLETS.md#4-x-onboard-and-verify-the-keys), preserving production cursors.
      1. [ ] [User] Compare affected wallet samples with their source wallets and expected script types; any mismatch blocks cutover.
   2. [ ] For required allocation proof, verify invoice/donation independence in isolation and confirm production cursors remain unchanged.

## 4. [ ] Prepare apex routing and discovery

1. [ ] Capture the public URL baseline: `/`, published `/learn/*`, assets, robots, sitemap, terms, and privacy.
   1. [ ] Record statuses, HTTP/`www`/slash redirects, canonicals, social metadata, structured data, and indexing signals.
   2. [ ] [Guided User] Capture existing Search Console/Bing property and sitemap status.
2. [ ] Prepare nginx/Compose for the Laravel apex landing page and separate content container.
   1. [ ] Preserve content paths, assets, and baseline redirects.
   2. [ ] Make apex public pages crawlable with correct robots/sitemap/canonicals; retain alpha/staging and invoice noindex.
3. [ ] Test existing alpha-issued public/signed links; prepare retained-alpha handling where redirects would break them.
4. [ ] Remove the content site's pre-release GitHub nav link, retaining its footer link; verify app/content navigation.
5. [ ] Record DNS/TTL cutover and recovery values, preserving mail and webmaster-verification records.
6. [ ] Prepare certificate issuance while normal apex traffic still goes to Pages, plus renewal compatible with nginx owning port 80.
7. [ ] Rehearse the prepared routing with the intended hostnames and record the passing app/site tags.

## 5. [ ] Verify mail readiness

1. [ ] Check current mail configuration and delivery evidence against [M20.5 §3](x20.5_LIVE_MAINNET_VALIDATION_BACKOUT.md#3-x-mail-sanity-on-mainnet); resolve any drift. Apex send/callback checks belong to M21.2 §5, inbox review to M21.3 §3.
2. [ ] Verify production aliasing is off and non-prod containment remains enabled.
3. [ ] Record existing Mailgun registrations and prepare the apex callback change.
   1. [ ] Plan continuity for pre-cutover events without duplicate registrations.
4. [ ] Determine whether a mailer upgrade/switch triggers [#81](https://github.com/n8bar/CryptoZing/issues/81); assign the rerun to M21.3 §4 or retain its deferred trigger and owner.

2. [ ] Deploy and verify the isolated self-hosted service.
3. [ ] Repoint the content repo's `_layouts/default.njk` integration; verify a marketing-page event arrives.
4. [ ] Verify staging, signed-in app, and invoice pages send no analytics and Cloud receives no duplicate event.
5. [ ] Record migration success or a named deferral under the milestone's non-gating decision. This outcome determines §7's privacy wording.

## 8. [ ] Verify the release and self-host boundary

1. [ ] Land the required release fixes and verify the resulting artifacts.
2. [ ] Run the [self-host guide](../ops/get-live/README.md) in an isolated blank environment.
   1. [ ] Verify the base recipe starts without our overlay or production configuration.
   2. [ ] Complete wallet onboarding and invoice creation with test-owned public keys.
   3. [ ] Verify the image contains no CryptoZing article site and a blank donation key leaves the donation page absent.
3. [ ] Correct discrepancies in the published guide.
4. [ ] Hand Phase 2 the verified tags, configuration/DNS/webhook changes, recovery record, analytics disposition, and user-owned cutover actions.

## Exit Criteria

- [ ] Recovery, wallet/mail readiness, and clean self-host checks pass for the candidate.
- [ ] Routing/TLS preparation and reviewed legal copy are ready for cutover.
- [ ] No unresolved prerequisite remains; analytics and #81 have explicit dispositions.
